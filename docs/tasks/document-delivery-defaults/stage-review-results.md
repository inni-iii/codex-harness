# 단계별 사용자 검토의 현재 절차 검토

## 최신 요구와 변경

기본은 요구 문서로 프로젝트 구현을 맡겨도 1단계만 수행한 뒤 결과를 보여주고 사용자 다음 지시를 기다리는 방식이다. 자료 확인→요구 정리→질문→성공 조건/계획→한 기능 구현→기능 검증/수정→다음 작업 판단→최종 정리가 전체 안내다. 기능이 여러 개이면 5/6/7에서 사용자 검토·선택을 거쳐 반복한다. 명시적으로 자율 진행을 맡긴 범위만 중간 검토를 생략할 수 있다. 이전 results.md는 자동 진행으로 잘못 해석했던 당시 관측이며 현재 계약의 의미 근거로 사용하지 않는다.

## 작성자 자체 시나리오

별도 모델/사용자 실험이 아닌 원문·절차 대조다.

| 입력·상태 | 수행할 현재 범위와 멈출 위치 |
|---|---|
| 문서 + 구현해줘 | 1단계 자료·환경만 확인해 결과/미확인/다음 예정을 보고하고 멈춤 |
| 1단계 결과 후 다음 단계 진행해 | 2단계 요구·출처·가정·미결정을 정리하고 다시 멈춤 |
| 현재 결과의 수정 요청 | 현재 단계에서 보완해 다시 보여주고 다음으로 넘어가지 않음 |
| 침묵 또는 시간 경과 | 다음 진행의 승인으로 기록하지 않고 현재 단계 유지 |
| 중요한 조건 질문 | 실제 답변과 남은 결정을 정리; 단계별 모드에서는 다음 단계 독립 작업도 미리 하지 않음 |
| 4단계 계획 확인 후 구현 진행 | 선택한 한 기능의 입력→처리→결과를 연결하고 변경/작동/미확인을 보고한 뒤 멈춤 |
| 5단계 결과 후 검증해줘 | 해당 기능의 관련 실행·검사·실패 수정/회귀를 수행하고 검증 결과를 보고한 뒤 멈춤 |
| 6단계 검증 실패 | 승인된 검증/수리 범위에서 재현·수정·관련 재검증 후 상태 보고; 다음 기능 자동 착수 금지 |
| 7단계 다음 기능 제안 | 사용자가 선택한 뒤 필요한 계획 보완 또는 다음 기능 5단계 진행 |
| 남은 시간 부족 | 선택 기능 보류/안정화를 제안하고 결정 대기; 필수 요구나 미실행 상태를 통과로 바꾸지 않음 |
| 설계만 요청 또는 작은 기존 수정 | 각각 현재 요청 범위에서 수행; 전체 프로젝트 구현·8개 task 생성으로 확대하지 않음 |
| 이후는 알아서 끝까지 해줘 | 명시된 범위에서만 기능별 검증 후 다음 선택을 자율 진행; 이후 단계별 검토 정정이 우선 |

## 실제 검사 범위와 한계

추가한 회귀는 기본 plan/implement 및 request-only requirements/plan 라우트가 해당 원문을 실제로 읽는지, 무관한 종류를 선택하지 않는지와 구현 준비 gate/현재 노드 유지 여부를 확인한다. 사람 검토를 기다리는 의미상 판단은 작성자가 지침을 대조한 것이며 도구가 사용자 승인/정지 행동을 기계적으로 인증한 결과는 아니다. 실제 서비스 완주·해커톤 품질·독립 모델 평가는 미수행이며 제품 UI 변경이 없어 E2E 비적용이다.
