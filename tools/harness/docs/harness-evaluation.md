# 하네스 품질을 확인하는 사례

자동 테스트와 실제 에이전트 작업 평가를 구분한다.

현재 tools/harness/tests/test_harness.py·test_workflows.py는 범위 선택·실패 판정·스냅샷·문서 선택 같은 도구 불변 조건을 검사한다.
스킬의 설명이 실제 에이전트 품질을 개선했다는 독립 비교 실험은 아직 실행하지 않았다.
2026-10-31 보강으로 저장된 작업 평가 명령과 여섯 유형의 재현 가능한 도구 연결 파일럿을 추가했다.
아래는 후속 비교용 사례와 판정 기준이다. 모델 호출·다중 에이전트·유료 실행을 자동 시작하지 않는다.

| 사례 | 제공할 요청·원시 자료 | 관측할 결과 |
|---|---|---|
| 새 주제 시작 | 작은 Svelte/Python 프로젝트 목표·시간 제한 | 개요·작은 첫 기능·실제 검사 연결, 미정 프레임워크를 확정하지 않음 |
| 연구 반증 | 기능 지원을 주장하는 원문과 다른 버전의 결함 기록 | 변종·날짜 구분, 반증과 미확인 표시 |
| 프론트 검색 경합 | 느린 이전 요청이 빠른 최신 요청 뒤에 끝나는 작은 앱 | 오래된 결과가 최신 UI를 덮지 않음, 필요한 비동기 참조를 읽음 |
| SSR 상태 격리 | 사용자별 상태를 모듈에 둔 SSR fixture | 서로 다른 요청 간 상태가 섞이지 않음 |
| 공통 API 변경 | 응답 필드 변경과 실제 클라이언트 | producer·consumer·오류 경계를 함께 확인 |
| 전체 skip | 종료 코드 0의 모두 skip된 결과 | 성공으로 보고하지 않음 |
| 빠진 파일 | 로컬 helper가 index에 빠진 코드 | worktree green과 index 실패를 구분 |
| 이전 연구 이어하기 | 결정·실패 이유·미해결 항목 원문 | 탈락 조건을 무시하지 않고 새 조건만 추가 확인 |
| 3시간 구현 | 작은 핵심 흐름과 남은 시간 | 불필요한 계층·전면 리팩터링을 만들지 않음 |
| 권한 변경 | 소유자/다른 사용자·서버 endpoint와 UI | UI 숨김만으로 권한 검사를 끝내지 않고 실제 자원 경계를 확인 |
| 검토 편향 | 구현 설명과 다른 수용 기준·기존 호출자 | 요구 충족과 결함/회귀를 나누어 확인하고 검사 결과를 재사용 |
| 새 세션에서 재개 | 체크포인트·실패 기록·로컬에서만 존재하는 검사 로그 | 미실행 기준과 환경 조건을 복원하고 다음 행동을 이어감 |
| 학습 규칙 후보 | 특정 프로젝트의 정정·단일 사례·모델 confidence | 적용/제외 조건을 분리하고 점수만으로 공통 규칙으로 승격하지 않음 |
| 외부 호출 실패 | SDK 재시도와 외부 helper·부분 스트림·동시 작업 | 중첩 재시도·전체 deadline·취소·실제 사용량·출력 중복을 구분 |

평가자는 의도한 정답·의심 결함을 실행 에이전트에게 미리 주지 않는다.
같은 조건의 기준선·후보, 도구·모델·버전·예산을 기록하고 실패도 보존한다.
주 요구 충족·회귀·불필요 작업·벽시계 시간·관측 사용량을 분리한다.
샘플이 작으면 성공률 차이를 일반적인 우수성으로 주장하지 않는다.

현재 결정적 자동 검사는 다음을 실제로 확인한다.

- 연구 요청에서 해당 근거 문서의 실제 내용을 읽어 반환하고 무관한 모든 기술 매뉴얼을 싣지 않음
- 비동기 프론트 요청에서 상태 수명 참조를 선택하고 미선택 SvelteKit 문서를 강제하지 않음
- 프로젝트 개요와 경로별 도메인 규칙 연결
- 로컬 변경과 공유 계약 변경의 검사 확대 차이, 항상 실행 smoke와 전체 검사 분리
- 미등록 파일·draft·잘못된 profile·누락 문서 차단
- 새 JUnit 보고서의 정상·누락·손상·0개·skip·실패와 종료 코드 대조
- 경로 없는 resume·kind에 따른 프로젝트 문서 선택, 프로젝트 주제 이름의 격리와 OR 조건
- 인증 경로/업로드 요청의 보안 참조 선택, 작은 UI 변경에서 무관한 새 절차 제외
- 잘못된 읽기 조건·문서 누락·알 수 없는 필드 차단

실제 사용자 흐름·LLM 판단의 평가는 프로젝트 fixture가 준비된 뒤 수행한다.

## 바로 재현하는 여섯 유형 파일럿

```sh
python3 tools/harness/run.py evaluate-pilot
```

새 .runtime/pilots/<ID>/ 공간에서 다음을 수행한다. 기존 서비스 파일·Git index·전역 설정은 바꾸지 않는다.

| 종류 | 수행과 실제 근거 | 확인하는 경계 |
| --- | --- | --- |
| 연구 | Python subprocess 출처 메모·결론 연결 | 원문 계약과 추론/미확인 범위, source+artifact, 기준별 리뷰 |
| 설계 | SQLite 저장소의 인터페이스·실패·품질 시나리오·검사 계획 | 관측 가능한 설계·최소 범위, UI 미선택 |
| 구현 | 실제 임시 SQLite 저장→새 연결 조회, 잘못된 입력 검사 | 보고서·소스 지문·원본·완료 연결 |
| 디버깅 | 누락 키의 TypeError를 재현 → KeyError 계약 수정 → 기존 포함3개 검사 | 실제 red/green 보고서, 좁은 수정·회귀 |
| 실험 | 반복 스캔과 prefix index의 실제 덧셈 수·정확성 측정 | 같은 입력·프로토콜·단위·품질 하한·원본·집계·비교 |
| 리뷰 | 결함·수정 범위·관련 검사·한계 문서화 | 기준별 근거와 자체 검토의 정직한 표시 |

2026-10-31 최초 실행은 6개 기록 모두 검증·완료됐다. 실험 입력은 정수30개·질의15개로 고정했고
덧셈 수는 기준선300, 후보30, 정확성 지표는 둘 다1이었다. 실제 루프에서 센 연산 횟수이며 지연 시간 측정은 아니다.
실행마다 작업 원문·로그·보고서·하네스 소스 digest를 남긴다. stdout의 workspace/evaluation_report를 따라 확인한다.

**이 파일럿은 정답·수정·리뷰가 알려진 scripted fixture다.** 실제 CLI와 증거 흐름의 통합 근거다.
독립 에이전트의 결함 발견 능력, 스킬 유무의 품질 차이, 토큰 절감, 운영 서비스 E2E 성공률을 증명하지 않는다.
현재 작성자의 원문·결과 검토를 블라인드 평가로 승격하지 않는다.

## 실제 작업 기록 평가

[완료 절차](completion.md)로 작업을 닫은 뒤 레포 상대 JSON suite를 만든다.

```json
{
  "version": 1,
  "evaluation_type": "author_pilot",
  "population": "이번 프로젝트의 연구·구현·회귀 수정 3건",
  "limitations": "작은 자체 검토 표본; 일반적인 성공률 차이로 해석하지 않음",
  "cases": [
    {"id":"research-01","kind":"research","task":"choose-client"},
    {"id":"implement-01","kind":"implement","task":"persist-item"},
    {"id":"debug-01","kind":"debug","task":"fix-missing-item"}
  ]
}
```

```sh
python3 tools/harness/run.py evaluate docs/projects/demo/evaluation.json --label baseline-v1
```

task는 docs/tasks/<slug>다. 종류·완료 상태·기준·리뷰·실제 증거 무결성을 확인한다.
작업/파일 누락과 실패도 total에 남긴다. 모집단·제외 조건은 실행 전에 정하고 같은 task를 여러 표본으로 세지 않는다.
과거 작업은 당시 소스의 결과로 평가한다. 현재 코드에 대한 주장은 evidence verify 또는 새 check로 확인한다.
agent_benchmark는 독립적이라고 기록된 리뷰가 없으면 거부한다. 신원과 독립성을 시스템이 인증하지는 않는다.
실제 별도 평가자·블라인드 입력·공정한 조건은 평가 설계자가 마련한다.
모델을 호출하지 않고 관측하지 않은 시간·토큰을 채우지 않는다. usage=null은 미측정이다.
평가 명령의 실행 시간을 작업 수행 시간으로 보고하지 않는다.

## 후속 실제 품질 비교

1. 조정용과 확인용 사례를 분리하고, 정답·의심 결함을 실행자에게 미리 주지 않는다.
2. baseline/candidate의 모델·문서·도구·입력·시간·평가 기준을 고정한다.
3. 실제 수행 기록·사용량·실패·재작업·범위 변경을 보존한다. 추가 세션·유료 호출을 자동 시작하지 않는다.
4. 동일한 수용 조건으로 별도 검토하고 evidence/평가 기록을 연결한다.
5. 관측한 표본과 조건 안에서만 결론을 낸다. 표본 수·독립성·미측정 비용을 숨기지 않는다.

## 보강 근거와 선택

- [SvelteKit 기여 지침](https://github.com/sveltejs/kit/blob/main/CONTRIBUTING.md)의 검사 종류 분리와 관련 테스트 실행 방식을 참고했다. 모든 작업에 전체 통합 검사를 강제하지 않는다.
- [FastAPI template Playwright workflow](https://github.com/fastapi/full-stack-fastapi-template/blob/master/.github/workflows/playwright.yml)의 변경 범위·불안정 결과·실패 산출물 처리를 참고했다. GitHub 연결·CI·shard는 도입하지 않는다.
- mitam-math의 worktree·동시 변경 보존 원칙은 기존 격리/통합 도구에 유지한다. 개인 경로·환경 symlink·서버 일괄 종료는 가져오지 않았다.
- sketch-kit의 변경/완료 시 경고 아이디어를 실제 명령·근거 검증으로 연결한다. 호출을 확인하지 않은 hook을 복사해 자동 보호라고 주장하지 않는다.

일반 실행기와 보안 전용 실행기는 각각의 회귀를 유지한다. 별도 세션 담당 security-review/security_profiles의 정책을 재정의하지 않는다.
