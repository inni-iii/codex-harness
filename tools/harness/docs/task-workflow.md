# 공통 작업 규격 초안

작성일: 2026-10-30 / 상태: 초기 설계 기록

현재 사용 절차는 [workflows.md](workflows.md), 구현된 검사 범위는 [verification.md](verification.md)를 따른다.
이 문서의 자동 오케스트레이션·모델 재선택 항목은 계속 후속 설계다.

연구·설계·구현·검증 작업을 같은 틀로 설명하고, 결과와 근거를 다음 작업으로 전달한다.
이번 초안은 작업 하나의 입력, 진행 과정, 완료 판정을 다룬다. 실행 코드나 기존 라우팅 정책에 적용된 규칙은 아니다.

## 출발점

기존 대화에서 확인한 요구는 다음과 같다.

- 여러 연구·설계·구현 작업에 공통으로 사용할 하네스를 만든다.
- 사용자의 반복 검토 부담을 줄이도록 수행과 검증·보완을 자동화한다.
- 모델과 추론 강도를 고르는 라우터를 포함하고, 테스트·리뷰·완료 조건도 구성한다.
- 연구에서 구현으로 넘어갈 때 결정과 근거를 이어받는다.

아래의 작업 단위, 항목, 진행·판정 방식은 이번에 검토할 제안이다.

## 작업 하나의 단위

작업은 목표와 결과물이 있고, 그 결과를 기준에 대조해 평가할 수 있는 단위로 잡는다.
태스크와 대화 세션은 같은 단위일 필요가 없다. 한 세션에서 여러 작업을 진행하거나, 한 작업을 여러 세션에서 이어갈 수 있다.

연구 → 설계 → 구현처럼 결과를 이어받는 경우에는 앞 작업의 결과를 다음 작업의 입력으로 연결한다.
작업 분할은 결과를 따로 평가할 필요와 의존성을 기준으로 정하며, 모든 요청에 같은 단계를 강제하지 않는다.

## 작업을 설명하는 공통 항목

| 항목 | 담을 내용 |
| --- | --- |
| 목표와 결과물 | 해결할 문제와 전달할 결과물. 단순히 수행할 행동만 적지 않는다. |
| 범위와 제약 | 포함할 일, 제외할 일, 지켜야 할 사용자 결정과 작업 경계. |
| 입력과 맥락 | 원래 요청, 프로젝트 위치, 관련 자료, 이전 결정과 근거. 확인하지 못한 입력도 구분한다. |
| 수행 계획 | 필요한 조사·분석·작성·실험의 순서와 의존성. 작은 작업은 짧게 표현한다. |
| 완료 기준과 검증 방법 | 결과가 충족해야 할 조건과, 각 조건을 어떻게 확인할지. |
| 결과와 검증 근거 | 실제 결과물, 기준별 확인 결과, 근거의 위치와 확인 조건, 남은 불확실성. |
| 다음 행동과 인수인계 | 보완할 일, 진행을 막는 이유, 다음 작업에 전달할 결정·근거·미해결 사항. |

하네스가 요청과 맥락에서 항목을 먼저 정리하고, 확인된 요구와 제안을 구분한다.
결과를 바꾸는 정보가 부족하면 필요한 부분을 묻고, 그 답변에 의존하지 않는 일은 계속 진행한다.
사용자가 모든 항목을 직접 작성하거나 매 단계 승인하는 흐름을 기본으로 가정하지 않는다.

## 공통 진행 과정

1. **목표와 완료 기준 정리**: 요청의 목적·범위를 확인하고 확인 가능한 완료 조건을 적는다.
2. **맥락과 현재 상태 확인**: 관련 자료와 기존 결과를 읽고 사실·가정·미확인 사항을 구분한다.
3. **수행 계획 결정**: 필요한 작업과 검증 방법을 정한다. 새 근거가 나오면 계획을 갱신한다.
4. **수행**: 작업 종류에 맞는 조사·설계·구현·평가를 진행한다. 중간 결과도 필요에 따라 검증한다.
5. **검증과 리뷰**: 결과를 완료 기준에 대조하고 오류·누락·반례를 확인한다.
6. **보완과 재검증**: 부족한 근거를 보충하거나 결과를 수정한 뒤 영향을 받은 기준을 다시 확인한다.
7. **완료 판정과 인수인계**: 충족 여부와 근거·한계를 보고하고 다음 작업에 필요한 내용을 전달한다.

검증에서 구현 문제가 나오면 수행으로, 전제나 요구의 문제가 나오면 맥락 확인이나 목표 정리로 돌아간다.
단계별 에이전트 분리, 모델 선택, 도구 구성은 이 진행 과정에 연결할 별도 설계 사항이다.

## 완료와 진행 불가의 구분

완료 판정은 필요한 완료 기준의 충족을 근거로 설명할 수 있을 때 내린다.
검증 결과에는 확인한 조건과 대상이 드러나야 하며, 추론이나 미실행 검사를 통과 근거로 사용하지 않는다.
프로세스 종료, 모델의 완료 선언, 일부 테스트 통과만으로 전체 요구 충족을 대신하지 않는다.

자동으로 고칠 수 있는 범위의 문제는 보완 대상으로 둔다. 정보·권한·환경이 부족하거나 해결 경로를 찾지 못했으면,
완료로 처리하지 않고 확인된 결과, 미충족 기준, 진행에 필요한 것을 남긴다.
미해결 항목이 완료 범위를 바꾸는 경우에는 기존 기준을 조용히 낮추지 않고 범위 결정이 필요함을 알린다.

실패 원인은 맥락 부족, 도구·환경 문제, 결과물의 결함 등으로 구분해 다음 행동을 정한다.
모든 실패를 모델 능력 부족으로 취급하지 않는다. 재시도 횟수·예산·중단 판단과 모델 재선택 정책은 후속 설계로 둔다.

## 인수인계 내용

다음 작업에는 목표·현재 결과·중요한 결정과 이유·근거 위치·미해결 사항을 전달한다.
조사자의 추천, 사용자가 선택한 결정, 실제 검증된 사실을 구분한다.
자료와 검증 기록은 확인 가능한 원본 위치를 연결하고, 필요한 맥락이 빠진 요약만으로 원문을 대체하지 않는다.
저장 위치·자동 탐색·공유 범위는 이후 인수인계 설계에서 정한다.

## 기존 라우터와 후속 설계

현재 [라우터 계약](contracts.md)의 작업 분류와 추천 결과는 공통 작업 진행에 연결할 수 있는 입력이다.
라우터의 `ready`는 실행 후보를 선택했다는 뜻이며, 이 초안의 업무 완료 판정과 구분한다.
이 문서는 기존 계약의 필드·상태 이름·정책을 변경하지 않는다.

다음에는 이 공통 틀에 연구·설계·구현별 수행 절차와 검증 기준을 하나씩 채우고 실제 작업 예시로 확인한다.
모델·추론 설정, 반복 한도, 별도 리뷰어 배정, 세션·하위 에이전트 구성, 저장 형식은 미확정이다.
