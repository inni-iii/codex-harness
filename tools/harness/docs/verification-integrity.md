# 검증 결과 재사용·완료·반복 실험의 무결성

2026-10-31 후속 점검. 정상 결과의 통과뿐 아니라 손상된 기록·동시 편집·반복 원본 혼동의 반례를 재현했다.
관련 구현은 checks.validate_result, evidence의 기록 변경 감지, experiments.verify_report다.
회귀 사례는 tools/harness/tests/test_verification_integrity.py에 둔다.

## 캐시와 보고서의 통과 표시를 다시 대조하기

캐시가 올바른 JSON이어도 객체가 아니거나 개별 항목 형식이 틀리면 재사용하지 않는다.
기존의 파일 해시 확인에 더해 다음 실행 사실과 원본 요약을 확인한다.

- 종료 코드는 실제 정수0이어야 하며 execution_error/summary_error가 없어야 한다.
- 캐시의 check ID·동작 검사 여부는 현재 등록한 검사와 일치해야 한다.
- unittest/JUnit 요약은 원본 로그/XML에서 다시 읽고 실행·skip·실패·expected failure·flaky 수를 대조한다.
- 0개 실행, 전체 skip/expected failure, 실패한 원본, 허용하지 않은 flaky는 passed 표시가 있어도 거부한다.
- 원본 삭제·해시 불일치·실행 예산을 넘는 로그·요약과 다른 집계도 재사용하지 않는다.

손상된 캐시는 정답으로 채택하거나 모든 검사를 막는 대신 해당 검사를 새로 실행한다.
정상 캐시의 검증은 로컬 파일/요약 대조이며 검사 프로세스를 다시 시작하는 것이 아니다.
구조화 JSON과 원본 요약을 읽는 양에도 제한을 둔다.

증거 등록과 완료 검토도 같은 validate_result를 사용한다. 캐시에만 엄격한 판정을 두고
task가 연결한 report.json에는 passed 문자열만 확인하는 불일치를 피한다.
test_summary와 allow_flaky를 실행 결과에 남겨 후속 해석 조건을 알 수 있게 한다.

예: 원본은 1개 통과인데 캐시의 test_count가0이거나 failed_count가1이면 모순이다.
해시가 맞더라도 원본이 실제로 0개 실행이라면 재사용하지 않는다.
종료 코드만 사용하는 사용자 정의 assertion/lint/build의 종류와 증명 범위는 별도로 리뷰한다.
이 검증이 모든 검사 명령의 의미나 악의적으로 작성된 결과의 실행 진위를 인증하는 것은 아니다.

## 완료 판정 도중의 기록 변경 보존

evidence add는 작업 기록을 읽을 때 해시를 보관하고, 실제 저장 직전에 같은 기록인지 확인한다.
finish는 작업과 리뷰의 시작 상태를 잡고 평가 후 다시 대조한다.
완료에 연결하는 리뷰 해시는 평가 시작 시의 해시이며 평가 후 바뀐 리뷰를 새로 해시해 통과 결과에 붙이지 않는다.

다른 세션이 목표·기준·리뷰를 바꾸거나 파일을 삭제하면 최신 기록을 덮어쓰지 않고 오류/needs_revision으로 남긴다.
새 기록을 읽고 바뀐 요구·근거·판정을 대조한 뒤 필요한 검사만 다시 수행한다.
기록만 바뀌었고 검사 대상은 그대로라면 유효한 검사 원본까지 무조건 재실행하지 않는다.

이것은 낙관적 변경 감지이며 OS 잠금·다중 파일 트랜잭션이 아니다.
검사와 파일 교체 사이의 모든 외부 쓰기를 봉쇄하지 않으므로, 한 작업 기록에는 한 작성자를 두고
독립 작업은 기존 worktree 절차로 분리한다. 감지된 충돌을 조용히 어느 한쪽 내용으로 덮어 수렴시키지 않는다.

## 반복 실험의 원본과 실제 명령 연결

같은 metrics 값을 여러 번 얻는 것은 정상일 수 있지만 같은 원본 파일을 여러 번의 독립 실행처럼 세면 안 된다.
검증 시 다음을 확인한다.

1. trial 인덱스·seed 순서가 선언과 맞고 실행 오류 없이 정수 종료 코드0을 얻었는가.
2. 반복마다 해당 실행 디렉터리 안에 독립적인 metrics.json과 output.log가 있는가.
3. 서로 다른 반복이 원본 파일을 공유하거나 다른 실행 디렉터리의 결과를 섞지 않았는가.
4. 기록한 실제 argv·cwd가 선언한 후보·seed·trial·metrics/output 경로·인터프리터에 대응하는가.
5. 선언한 입력 전체의 해시 연결이 있고, 원본·지표·품질 하한·전체 집계가 일치하는가.

명령 비교는 실제 실행 때와 같은 순서로 자리표시자를 치환한다.
과거 기록은 당시 workspace/interpreter에 묶어 해석한다. 다른 노트북의 현재 경로로 과거 실행 명령을 꾸며 바꾸지 않는다.
필수 구조가 손상된 JSON은 검증 오류로 반환하며 traceback이나 통과 결과로 처리하지 않는다.
기록한 파라미터를 측정 코드가 실제 사용했는지, 계측 코드가 타당한지는 리뷰와 별도 실험 설계의 책임이다.

## 비용과 적용 시점

새 검사 단계나 다중 에이전트를 매 요청에 추가하지 않았다.
cache 재사용·증거 등록/완료·실험 결과 확인이라는 기존 지점에서 추가 무결성 검사를 한다.
실제 검사 실행 범위·checkpoint·E2E 시점은 기존 [검증 계약](verification.md)과 [완료 계약](completion.md)을 유지한다.
반례 수정 후 관련 회귀를 먼저 실행하고 마지막에 등록 검사 전체와 알려진 답의 파일럿을 확인한다.
이 결과를 실제 서비스 E2E나 독립적인 에이전트 품질 보증으로 확대하지 않는다.
