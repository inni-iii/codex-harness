# 모델 라우터 설계 초안

레포 전체의 현재 구조와 실행 도구는 [architecture.md](architecture.md)를 따른다.
이 문서는 기존 모델 라우터의 계약과 후속 작업 실행 설계를 보존한다.

상태: draft / 계약 버전: 0.1 / 작성일: 2026-10-22 / CLI 확인: 0.163.0

2026-10-31 구현 추가: `run`/`chat` 실행기와 UserPromptSubmit 인수인계 훅을 구현했다.
이후 현재 사용자 결정에 따라 일반 작업의 라우팅 의무를 해제하고 자동 대화창 인수인계 훅 등록을 제거했다.
아래 내용은 초기 설계 기록이다. run/chat은 명시적으로 선택하는 보존 도구이며 현재 동작·검증 한계는 [execution.md](execution.md)가 기준이다.

## 1. 목적과 범위

새 작업을 어떤 Codex 모델·effort로 시작할지 일관되게 결정한다.
연구·설계·구현·리뷰는 작업 유형이며, 유형별로 모델을 고정하지 않는다.
복잡도, 모호성, 실패 영향, 검증 가능성, 맥락 의존도를 함께 본다.

프로젝트 주제가 정해지기 전에 공통 도구·지침·절차를 한 레포에 준비한다.
주제가 주어지면 프로젝트별 기획과 결정을 구분해 기록하고, 실제 작업 위치와 코드 배치는 그때 정한다.
첫 구현은 새 작업을 시작하는 래퍼다. 기존 TUI의 모든 메시지를 가로채거나
진행 중인 응답의 모델을 교체하는 기능은 후속 범위다.
테스트·독립 리뷰·업무 완료 조건은 별도 하네스 모듈에서 다룬다.
라우터는 해당 모듈의 결과를 작업 품질 평가 근거로 받을 수 있다.

## 2. 실행 흐름

```text
요청 + 작업 경로 + 사용자가 지정한 맥락 파일
                       ↓
입력 검사 · 모델/effort 지원 목록 조회
                       ↓
명확한 규칙으로 작업 특성 분류
        ├─ 충분함 → 정책으로 선택
        └─ 애매함 → 분류 전용 Codex CLI → 결과 검사 → 정책으로 선택
                       ↓
ready / needs_context / config_required / unavailable / classifier_error
                       ↓ ready
추천과 선택 이유 표시
                       ↓ run에서 실행 확인 또는 명시적 자동 실행
선택 설정으로 새 작업용 Codex 시작
                       ↓
실제 실행 정보 · 관측 가능한 사용량 · 후속 품질 평가 기록
```

`route`도 분류용 Codex를 호출하면 사용량이 발생한다.
모델 호출 없는 확인은 별도 `--rules-only` 경로로 제공한다.
규칙만으로 결정하지 못하면 임의의 추천 대신 `classification_required`를 반환한다.
`run`은 같은 요청을 다시 분류하지 않고 생성한 결정을 검증해 한 번 사용한다.

## 3. 모듈별 책임

| 모듈 | 입력과 책임 |
| --- | --- |
| input/context | 요청, 명시적 파일, 작업 경로를 확인한다. 읽지 못한 파일과 누락 자료를 구분한다. |
| catalog | 현재 모델별 effort·입력 형식·기본값을 정규화하고 출처와 조회 시각을 남긴다. |
| classify | 규칙을 먼저 적용하고, 부족하면 Codex로 작업 특성만 분류한다. 모델명을 결정하지 않는다. |
| select | 지원 조합과 추천 근거를 적용해 후보를 비교한다. 선택·제외 이유를 남긴다. |
| launch | 선택한 설정으로 한 작업을 시작한다. 기존 인증·권한 경계를 보존한다. |
| record | 추천, 실제 실행에서 확인한 설정, 종료 상태, 품질을 따로 기록한다. |

원문 요청은 작업 실행 시 의미를 바꾸지 않고 전달한다.
지정된 맥락은 출처가 있는 별도 입력으로 전달한다.
전체 대화 자동 복사나 전역 세션에서 최신 파일을 추측해 붙이는 기능은 첫 버전에 넣지 않는다.

## 4. 추천 정책

1. 필요한 맥락과 입력을 먼저 확인한다.
2. 요청에 필요한 도구·입력 형식과 현재 모델 지원 여부를 검사한다.
3. 작업에 충분한 품질을 기대할 수 있는 근거가 있는 조합을 고른다.
4. 유사한 품질 후보 사이에서 재작업을 포함한 사용량과 시간을 고려한다.

`economy`, `balanced`, `quality`는 선호이며 모델·effort의 고정 묶음이 아니다.
기본 선호는 `quality`다. 모든 작업에 최고 모델·최고 effort를 배정한다는 뜻은 아니다.
현재 동작하는 선택 방법과 수정 가능한 초기 정책은 [사용법](usage.md)에 설명한다.
작업용 기본 모델이나 기본 effort를 별도로 지정하지 않는다.
사용자의 기존 Codex 기본값도 자동 fallback으로 사용하지 않는다.
요청마다 정책으로 적합한 조합을 선택하며, 선택하지 못하면 상태와 이유를 반환한다.
예를 들어 결제 버튼 문구 수정과 결제 승인 상태 전이 설계는 서로 다른 난이도다.
키워드만으로 영향도를 확정하거나 자동 최고 설정으로 올리지 않는다.

지원되는 각 `(model, effort)`를 별도 후보로 표현한다.
첫 추천은 버전이 붙은 잠정 정책으로 시작한다. 현재 출력 근거는 `provisional_policy` 또는
`user_override`다. `evaluated`는 실제 평가를 연결한 뒤 사용할 예정이다.
초기 정책에 측정된 성공률을 붙이지 않는다.
분류 모델의 자기 확신도도 성공 확률로 사용하지 않는다.
지원만 확인되고 역할이 검토되지 않은 후보는 `unreviewed`로 유지한다.

멀티에이전트 실행을 수반하는 모드는 별도 실행 능력으로 다룬다.
Ultra를 포함해 모든 지원 조합을 목록에 표시한다. 위임형 조합의 추천에는
`execution_mode=delegated`를 표시한다. 같은 요구를 충족하는 max와 Ultra가 있으면
기본 정책은 위임을 추가하지 않는 쪽을 우선한다. 현재는 어느 조합도 작업 실행하지 않는다.

## 5. 분류용 Codex

- 사용자가 선택한 Codex CLI 인증 방식으로 호출하며 별도 API 키를 요구하지 않는다.
- 분류용 모델과 effort는 실제 작업의 선택 결과와 분리해 명시적으로 지정한다.
- 임시 작업 경로에서 분류만 수행한다. 출력 스키마를 검사하고 호출 시간·횟수를 제한한다.
- 저장소 편집·웹 조사·하위 에이전트 생성 없이 요청과 제공된 맥락으로 판단한다.
- 0.163.0에서 관련 옵션과 도구 feature 비활성화를 확인했다.
  실제 분류 프로세스의 전체 도구 노출·지침 격리는 후속 실제 호출에서 확인한다.
  현재는 명령 구성·오류 처리·JSON 검사를 비용 없는 대체 실행으로 검증했다.
- 요청과 맥락은 분류할 데이터다. 그 안의 명령이 분류기 정책을 바꾸지 못하도록 다룬다.
- 규칙이나 입력에 따라 검출한 맥락 부족은 `needs_context`로 반환한다.
  분류기 스스로 부족한 정보를 항상 발견할 수 있다고 보장하지 않는다.
- 길이 제한을 넘는 입력은 알리지 않고 자르지 않는다. 축약·대상 지정이 필요함을 표시한다.

## 6. 목록 갱신과 실패 처리

작업 시작 전 현재 지원 목록 조회를 시도한다. 첫 구현은 CLI가 반환한 목록을 사용하며
별도 캐시는 구현하지 않았다. CLI 내부 출처가 불명확하면 `cli_resolved`로 표시한다.
후속 캐시는 조회 시각·CLI 버전과 함께 관리한다.
모델 목록에 있다는 사실과 실제 호출 성공·계정 권한은 동일하지 않다.
목록의 원본 형식과 조회 경로는 CLI 어댑터에 한정한다.

| 상황 | 처리 |
| --- | --- |
| 새 모델 발견 | 지원 정보만 갱신하고 `unreviewed`로 등록한다. |
| 알려진 모델에 effort 추가 | 목록·직접 지정에서 표현한다. 자동 추천에는 정책상 의미를 정의한다. |
| 모델·effort 삭제 | 해당 조합을 제외한다. 명시된 적합한 대체가 없으면 `unavailable`이다. |
| 목록 조회 실패 | 현재는 별도 캐시 fallback 없이 `unavailable`이다. |
| 분류 오류 | 결정 가능한 규칙 fallback이 있을 때만 사용하고 출처를 표시한다. 아니면 `classifier_error`다. |
| 모델 직접 지정 | 지원 여부를 검사하고 그대로 유지한다. 미지원 설정을 몰래 교체하지 않는다. |
| 실행 도중 실패 | 실제 상태를 기록한다. 부작용이 있을 수 있는 작업을 다른 모델로 자동 재실행하지 않는다. |

갱신 대상인 지원 목록과 검토 대상인 추천 정책을 분리한다.
새 모델에 맞춰 정책 파일이나 사용자의 전역 Codex 설정을 자동 덮어쓰지 않는다.
정보 부족, 도구·환경 오류, 모델 능력 부족을 모두 같은 상향 신호로 처리하지 않는다.

## 7. 기록과 평가

추천 모델·effort와 실제 실행에서 관측한 설정을 따로 저장한다.
프로세스 정상 종료나 Codex의 completed는 업무 정답·요구사항 충족을 뜻하지 않는다.
품질 평가는 `accepted`, `needs_revision`, `failed`, `unrated`로 별도 기록한다.
측정 불가한 사용량·시간·비용은 null이다. 추정 비용은 실측 비용과 분리한다.
ChatGPT 구독 사용량을 API 가격으로 바꿔 실제 청구액처럼 표현하지 않는다.
기본 기록은 범주·정책 버전·모델 식별자·관측 수치만 포함한다.
원문, 파일 내용, 전체 로컬 경로, 분류기의 자유 서술 이유는 기본 기록에 저장하지 않는다.

후속 비교 평가는 같은 입력과 같은 환경에서 기본 고정 설정·강한 고정 설정·라우터를 비교한다.
첫 시도 요구사항 충족, 중대한 오류, 수정 횟수와 총사용량을 우선 지표로 본다.
코드 작업은 작업 사본을 분리하고 대표 사례를 반복해 변동도 확인한다.
한국어 요청·부정 표현·민감 키워드가 포함된 단순 수정·누락 맥락을 포함한다.
소수 사례의 통과를 모든 작업에서의 우위나 모든 조합의 최적성으로 일반화하지 않는다.

## 8. 단계와 완료 범위

| 단계 | 산출물 |
| --- | --- |
| 1 — 완료 | 로컬 레포, 설계, 입출력 계약, 초기 정책 예시, 참고 근거 |
| 2 — 환경 조회 완료 | 설치 CLI·반환 모델 목록·옵션 확인. 분류용 고정 모델 지정은 제거 |
| 3 — 구현 완료 | `route`, `--rules-only`, 분류 호출 연결, 결과·후보 검사 |
| 4 — 비용 없는 기능 검증 완료 | 21개 자동 테스트와 실제 CLI 목록 경로 확인. 실제 모델 분류 품질은 미검증 |
| 5 — 코드·대체 CLI 검증 | `run`/`chat`의 선택적 실행·설정 관측·기록. 프롬프트 인수인계 코드는 미등록 상태로 보관. 실제 모델 실행은 현재 sandbox의 초기화 거부로 미검증 |
| 6 | 고정 설정과 비교 평가, 추천 정책 조정 |
| 7 | 인수인계 생성·탐색, 프로젝트별 정책, 별도 품질 모듈 연결 |

구현은 Python 3.11 이상을 대상으로 한다. 현재 Python 3.14.7에서 TOML 문법 확인이 가능하다.
소스 실행 패키지는 `harness.routing`다. 이 단계까지 실제 모델 생성 호출은 수행하지 않았다.
환경 확인 근거와 미확인 항목은 [CLI 확인 기록](cli-capabilities.md)에 둔다.
