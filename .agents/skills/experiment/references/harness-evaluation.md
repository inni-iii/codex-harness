# 하네스와 스킬 자체를 평가하기

형식 검사는 스킬이 잘 작동함을 증명하지 않는다. 지침을 바꿀 때 실제 작업에서 달라질 행동을 먼저 정한다.

## 평가를 세 단계로 나누기

1. 정적 점검: metadata, 파일·참조·명령, 포터블 경로, 충돌하는 규칙.
2. 결정적 도구 검사: 조건에 맞는 문서 선택, 미등록 검사 차단, 실패·0개 테스트·오래된 결과 판정.
3. 실제 작업 평가: 같은 입력에서 스킬 유무·버전을 비교하고 요구 충족·회귀·불필요 작업·시간·사용량을 측정.

앞 단계 통과를 뒤 단계의 성공률 향상으로 보고하지 않는다.
[평가 사례](../../../../tools/harness/docs/harness-evaluation.md)는 재현용 입력과 관측 기준이다. 자동 모델 실행기는 아니다.
`evaluate-pilot`은 여섯 유형의 알려진 답을 재현하는 통합 검사다.
`evaluate <suite> --label <이름>`은 완료된 작업과 실제 증거를 평가한다. 독립적인 에이전트 품질 비교와 구분한다.

## 사례 구성

정상 기능 추가만 모으지 말고, 이전 작업 이어하기·연구 반증·SSR 상태 격리·공유 API 변경·테스트 전체 skip·변경 범위 누락을 포함한다.
사용자 요구와 원시 자료를 주고 결과를 판단한다. 의도한 답·예상 결함을 모델에게 미리 알려 주면 탐지 능력 평가가 되지 않는다.
지침을 조정한 사례와 별도 확인 사례를 분리하고, 실패한 사례도 보존한다.

## 결과 판정

- 실제 요구 동작: 출력/행동으로 확인. 함수 이름·특정 문구 존재만 검사하지 않는다.
- 회귀: 변경과 연결된 기존 동작, 권한·계약·공통 설정의 영향.
- 절차: 필요한 원문을 읽고 미확인 사실을 구분했는가.
- 효율: 불필요한 파일·반복 테스트·질문·설치·모델 호출이 늘지 않았는가.
- 비용: 관측한 사용량과 추정 가격을 구분한다.

코드 검사를 우선 사용하고, 주관적 품질은 명시적 기준에 따른 사람/모델 평가를 보조로 둔다.
평가자 동의만으로 사실이나 제품 수용을 판정하지 않는다.
실제 모델 실행은 사용 가능한 도구·권한·예산을 확인한 범위에서만 수행한다. 승인 없이 유료 비교나 다중 에이전트를 시작하지 않는다.
