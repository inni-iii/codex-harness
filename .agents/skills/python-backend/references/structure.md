# Python 구조와 작은 리팩터링

새 구조를 정하거나 기존 구조를 이동할 때 읽는다.

## 크기와 책임에 따라 선택하기

| 상황 | 시작점 | 분리할 신호 |
|---|---|---|
| 작은 스크립트·실험 | 명확한 함수와 입출력, 필요한 설정 | 같은 규칙이 복제됨·테스트가 어려움 |
| 작은 서비스 | 앱 진입점, 기능 모듈, 테스트 | HTTP·업무·외부 호출이 한 함수에 뒤섞임 |
| 기능이 여러 개인 서비스 | 기능별 패키지에 관련 router/schema/service 배치 | 기능 간 순환 의존·공통 정책의 중복 |
| 설치해서 쓰는 라이브러리 | pyproject와 설치 가능한 패키지 | 작업 디렉터리에 따라 import가 달라짐 |

src 레이아웃은 import·패키징 선택이고, 기능별 패키지는 책임 배치 선택이다. 둘을 같은 원칙으로 혼동하지 않는다.
기존 패키지가 잘 동작하면 작업 때문에 꼭 필요한 부분만 수정한다.
service·repository·models 파일을 세트로 반드시 만들지 않는다. DB가 없으면 models도 필요 없다.

기능이 자랐을 때의 예시:

```text
backend/
  pyproject.toml
  src/app/
    main.py
    config.py
    items/
      router.py
      schemas.py
      service.py
    integrations/
      search_client.py
  tests/
    test_items.py
```

위 트리는 예시이며 FastAPI·설치 방식·파일 수를 확정하는 scaffold가 아니다.
라우터는 전송 계층 변환, service는 업무 규칙, integration은 외부 프로토콜을 담당하게 할 수 있다.
현재 요구를 해결할 만큼만 분리하고 기능 간 import 방향을 설명할 수 있게 한다.

## 유지할 경계

- 사용자 입력·환경·외부 응답은 실제 타입과 검증 경계를 갖는다. 내부 전체를 Any로 만들지 않는다.
- 라이브러리/모듈 import가 네트워크·DB 연결·파일 쓰기를 시작하지 않게 한다.
- 앱 생성 시 필요한 설정·클라이언트를 주입하면 여러 테스트 앱의 상태를 격리하기 쉽다.
- 배치·CLI에도 쓸 업무 규칙이라면 HTTP Request/Response를 직접 받지 않게 분리한다.
- 실패를 None이나 빈 목록으로 덮기 전에 호출자가 구분해야 할 오류인지 확인한다.
- 공통 helper가 두 번째 호출자도 없이 과도하게 일반화되면 기능 안에 둔다.

## 리팩터링 순서

1. 이동할 코드의 호출자·테스트·관련 Git 이력과 과거 버그 보호 장치를 확인한다.
2. 현재 외부 동작을 확인할 검사를 확보한다.
3. 파일/함수 이동이나 의존성 방향 정리를 작은 단위로 수행한다.
4. import·entrypoint·작업 디렉터리·설정·테스트 수집 변화를 확인한다.
5. 관련 행동 검사와 공유 경계 검사를 실행한다. 동작 변화가 필요하면 이동과 구분한다.

시간이 짧으면 큰 계층 교체보다 테스트 가능한 함수 추출, 외부 호출 주입, 중복 계약 제거처럼 다음 구현을 쉽게 만드는 정리가 유리하다.
유일한 “Python 표준 아키텍처”라는 주장은 하지 않는다. 프로젝트 규모와 현재 규칙을 근거로 고른다.
