# 실패 원인을 찾을 수 있는 최소 관측

서버 로깅·외부 호출·오류 처리를 바꾸거나 재현되지 않는 실패를 조사할 때 읽는다.
프로젝트에 필요한 정보를 먼저 정하고 전체 모니터링 스택 설치를 기본값으로 삼지 않는다.

## 한 요청을 연결할 정보

event 이름, 검증한 요청 ID/작업 ID, 처리 단계, 결과, 소요 시간, 오류 종류를 일관된 필드로 남긴다.
요청 ID를 외부에서 받으면 길이·문자·신뢰 범위를 정하고 사용자 값을 무제한 그대로 기록하지 않는다.
원본 요청 본문·URL query 전체·토큰·비밀번호·개인정보를 기본 로그에 넣지 않는다.
사용자에게 보이는 오류와 서버 진단 정보를 분리하되 서버 로그도 무조건 안전하다고 가정하지 않는다.

| 단계 | 도움이 되는 정보 | 노출을 피할 정보 |
|---|---|---|
| 요청 수신 | 안전한 route/작업 종류·요청 ID | 쿠키·Authorization·원본 폼 |
| 업무 처리 | 단계·결과·안전한 자원 식별 범위 | 민감한 전체 객체 |
| 외부 호출 | 제공자·시도 수·상태·대기/처리 시간 | API key·전체 프롬프트·원문 응답 |
| 예외 | 오류 종류·추적 가능한 코드 위치 | 비밀이 포함된 예외 문자열/연결 URL |
| 완료 | 성공/실패·지연·취소 | 사용자 원본 콘텐츠 |

[OWASP 로깅 안내](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)에 맞춰 포함/제외 정보와 접근·보존 범위를 정한다.
구조화 JSON만으로 비밀값 마스킹이나 요청 격리가 보장되지는 않는다.

## 수명과 실패 경로

요청별 context는 시작 시 격리하고 완료·예외·취소 때 정리한다.
백그라운드 작업에 무엇을 전달할지 명시하고 다른 요청의 ID/사용자 상태가 섞이지 않는지 확인한다.
성공뿐 아니라 검증 실패·외부 timeout·예외·로그 기록 실패 때의 동작을 본다.
로그 실패가 업무를 어떻게 바꿀지는 해당 요구에 맞춰 정한다.

## 필요한 만큼 측정

지연은 연결 대기·큐 대기·외부 처리·전체 시간을 구분한다.
분모와 구간이 같은 실패율·지연을 비교한다.
메트릭 label에 사용자 ID·전체 URL·임의 입력을 넣어 무제한 종류가 생기지 않게 한다.
health는 프로세스 생존, readiness는 필요한 의존성 준비, 사용자 스모크는 실제 흐름을 각각 확인하도록 구분한다.
한 번의 health 200을 저장·권한·제품 흐름 검증으로 보고하지 않는다.

Prometheus·Grafana·Loki·분산 tracing은 실제 운영 요구가 생기면 선택한다.
현재 하네스의 검사 로그와 앱의 실제 관측 도구는 별개이며 자동 설치하지 않는다.
