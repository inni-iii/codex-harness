# 프론트와 백엔드의 API 계약

요청·응답·오류·인증 또는 생성 타입을 바꿀 때 양쪽에서 읽는다.

## 먼저 합의할 계약

경로·메서드, 입력 타입/필수/기본값/범위, 성공 status·payload, 실패 status·오류 코드, 인증·소유권, 페이지네이션·정렬, 시간·ID 표기를 확인한다.
현재 프로젝트의 계약과 일관성을 우선한다. 범용 하네스가 API 버전·envelope·camelCase를 일괄 결정하지 않는다.
타입이 같아도 단위(초/밀리초), 시간대, null/누락, 빈 목록 의미가 다르면 계약 결함이다.

| 변경 | 함께 확인할 대상 |
|---|---|
| 필드 추가·이름/타입 변경 | 응답 schema·생성 타입·클라이언트·UI·기존 소비자 |
| 오류 코드·status 변경 | 서버 handler·프론트 오류 분기·폼 상태 |
| 인증·쿠키·CORS | 비인증·잘못된 권한·SSR 요청·브라우저 연결 |
| 생성/중복 정책 | 연속 제출·재시도·멱등 키/유니크 제약 |
| pagination·정렬 | 빈 결과·동일 정렬값·다음 페이지·UI 이동 |
| streaming | 이벤트 형식·순서·실패·취소·재연결 |

## 타입 생성이 필요한 프로젝트

백엔드 schema/OpenAPI를 기준으로 선택한 생성 도구가 프론트 타입/클라이언트를 만들게 할 수 있다.
저장소의 실제 명령·고정 버전·생성 파일 처리 정책을 등록한다.

```text
백엔드 schema
  → 네트워크/실서비스 없이 schema export
  → 타입/클라이언트 생성
  → 생성물 차이 확인
  → 프론트 타입 검사
  → 실제 응답·오류 계약 검사
```

생성을 위해 운영 서버·DB를 요구하면 앱 factory·설정 분리로 로컬 export가 가능한지 검토한다.
생성물은 직접 수정하지 않고 원본과 생성 명령을 고친다.
검증용 생성은 임시 디렉터리에서 비교해 소스 변경 때문에 결과가 stale 되는 일을 피할 수 있다.
“타입 검사가 통과했다”는 “서버가 이 payload를 실제로 반환한다”의 증명이 아니다.
외부의 비신뢰 응답이 사용자 동작에 중요한 경우 런타임 검증 경계를 정한다.

## 요구에서 도출할 계약 검사

예: 항목 조회 API라면 성공 payload뿐 아니라 없는 항목, 다른 사용자의 항목, 잘못된 ID, 빈 결과를 요구에 맞게 확인한다.
HTTP 200 한 가지만 검사하지 말고 필요한 필드·의미·노출되면 안 되는 데이터도 확인한다.
정확한 status를 합의한 뒤 검사한다. 401 또는 403이면 아무거나 통과처럼 계약을 흐리지 않는다.
프론트 mock이 서버와 같은 잘못된 가정을 공유하지 않도록 실제 API와의 작은 연결 검사를 남긴다.

공유 schema·인증·설정 변경은 impacts로 양쪽 검사를 선택한다. 하네스는 파일명만으로 이 경계를 자동 추론하지 않는다.
