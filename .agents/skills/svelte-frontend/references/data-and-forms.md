# SvelteKit 데이터·인증·폼

프로젝트가 SvelteKit을 선택했을 때 읽는다. 일반 Svelte 앱에 load/action 파일을 추가하지 않는다.

## 데이터와 서버 경계

서버에서만 접근할 비밀값·DB 코드는 서버 전용 경계에 둔다.
페이지에 반환하는 데이터는 브라우저로 전달될 수 있으므로 세션 토큰·비밀 설정을 섞지 않는다.
라우트 load에서는 프로젝트가 제공하는 요청 fetch와 인증 전달 방식을 확인한다.
개인화된 결과의 캐시 키·사용자 범위를 명시한다. 모듈 변수에 마지막 사용자 결과를 저장하지 않는다.
load에서 데이터를 읽었다고 브라우저 모듈 singleton을 갱신하지 않는다.

새로고침 SSR, 클라이언트 내부 이동, 로그아웃 후 재방문, 다른 사용자 요청을 각각 고려한다.
컴포넌트 인스턴스가 재사용될 때 초기화한 값이 새로운 data/props를 따라가는지 확인한다.
SvelteKit 버전별 load·서버 전용 모듈·인증 지침은 [공식 문서](https://svelte.dev/docs/kit/loading-data)를 따른다.

## 인증과 권한

화면에서 버튼을 숨기거나 layout에서 redirect하는 것만으로 보호하지 않는다.
서버 action·endpoint·실제 자원 접근에서 요구된 권한을 검사한다.
SSR에서 쿠키/헤더를 백엔드로 보낼 때 목적지·도메인·허용 범위를 확인한다.
외부 임의 URL에 사용자의 인증 헤더를 그대로 전달하지 않는다.

## 폼 상태

입력 → 검증 → 제출 중 → 성공/오류를 구분한다.
사용자가 고쳐야 할 필드 오류와 서비스 실패를 구분하고 관련 입력을 보존한다.
중복 제출 방지 UI와 서버의 중복 처리 정책을 연결한다.
네트워크 오류 후 재시도를 하더라도 같은 요청이 이미 처리됐을 가능성을 고려한다.
민감한 입력은 실패 응답·URL·로그·분석 이벤트에 되돌려 넣지 않는다.

form actions를 쓴다면 [공식 안내](https://svelte.dev/docs/kit/form-actions)에 맞춰 기본 폼과 enhancement 동작을 확인한다.
JS 없이 동작해야 하는 요구가 있는 경우에만 해당 경로를 필수 검사로 둔다.
현재 버전의 actions·remote functions 등 선택지를 근거 없이 섞거나 일괄 마이그레이션하지 않는다.

## 확인할 관측 결과

- 유효한 제출이 실제 데이터와 UI에 반영되는가
- 필드 오류가 해당 입력에 연결되고 수정 가능한가
- 실패 뒤 loading이 풀리고 의도한 재시도가 가능한가
- 새로고침·뒤로가기·직접 URL 접근에서도 요구 상태인가
- 익명·권한 없는 사용자·다른 사용자 요청이 서버에서 구분되는가
- 프론트 mock과 실제 Python 응답의 의미가 일치하는가

프로젝트 계약에 해당하지 않는 항목은 이유를 남기고 제외한다.
