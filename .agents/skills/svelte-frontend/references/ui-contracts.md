# 공용 UI 계약과 접근성

컴포넌트·스타일·사용자 상태를 바꿀 때 읽는다.

## 먼저 기존 구현 찾기

컴포넌트 이름뿐 아니라 역할·props·상태·토큰으로 검색한다.
기존 primitive를 조합해 기능 UI를 만들고 같은 역할의 별도 버튼·입력 shell을 반복하지 않는다.
공용 API를 바꾸면 호출자를 확인하고 기존 사용처도 검증한다.

## 계약에 적을 내용

- 공개 props·이벤트·바인딩, 기본값, variant/size 의미
- 정상·hover·active·focus·disabled·loading·error 등 적용 가능한 상태
- 키보드 동작·label·role·focus 이동·닫힘 후 복원
- 의미 토큰, 반응형·긴 텍스트·빈 데이터의 동작
- 어느 데모·테스트·승인 기준으로 확인할지

특정 레포의 24/32/40px 버튼 규격이나 폰트를 범용 기본값으로 옮기지 않는다.

## 접근성에서 놓치기 쉬운 차이

- 클릭 가능한 div보다 의미에 맞는 button/link/input을 우선한다.
- 탭·라디오의 activeIndex만 바꾸고 실제 focus를 옮기지 않으면 키보드 계약이 미완성일 수 있다.
- 커스텀 선택 UI는 키보드·선택 상태·focus·스크린리더 의미가 함께 구현되어야 한다.
- dialog는 이름·초기 focus·내부 이동·닫힘·복원을 확인한다. 간단한 Tab 순환 코드만으로 모든 경우를 보장하지 않는다.
- icon-only 버튼은 컨트롤에 이름을 주고 장식 아이콘은 중복 낭독을 피한다.
- 로딩 skeleton은 장식과 상태 안내를 분리하고 reduced motion을 고려한다.
- disabled와 readonly, 빈 결과와 조회 실패를 혼동하지 않는다.
- 오류는 색만으로 전달하지 않는다. 오류 메시지와 해당 입력의 연결도 확인한다.

## 화면 상태와 회귀

처음 진입·로딩·성공·빈 결과·오류·재시도·긴 입력·작은 화면 중 관련 상태를 확인한다.
토큰·공용 primitive·app shell 변경이면 대표 사용처와 영향이 없어야 하는 인접 화면도 확인한다.
스크린샷은 보이는 상태를 보여 주지만 실제 키보드·네트워크·저장 동작을 증명하지 않는다.
타입 검사·빌드·컴포넌트 검사·브라우저 확인의 역할을 구분한다.

성능 최적화는 측정한 문제에 맞춰 한다. 가상 목록·lazy load·복잡한 전역 상태를 모든 화면의 기본 구조로 만들지 않는다.
