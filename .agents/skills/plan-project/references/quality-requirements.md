# 프로젝트의 품질 기준과 결정 기록

새 주제의 개요를 채우거나 구조 선택이 필요한 큰 변경에서 읽는다.
숫자는 실제 사용자 흐름·규모·예산에서 정하고, 예시 값을 기본 요구로 만들지 않는다.

## 필요한 기준 고르기

| 질문 | 적을 항목 | 확인 방법의 예 |
|---|---|---|
| 사용자가 어디서 기다리는가 | 응답 시간·입력 크기·동시성·측정 구간 | 대표 요청의 지연 분포 |
| 데이터가 얼마나 커지는가 | 현재/예상 규모·증가·최대 입력 | 조회·메모리·처리량의 작은 실험 |
| 무엇을 잃으면 안 되는가 | 저장 단위·중복·허용 손실·복구 조건 | 로컬 실패/복구·거래 단위 검사 |
| 누가 무엇에 접근하는가 | 역할·소유권·데이터 민감도 | 서버 경계의 접근 검사 |
| 비용이 드는 경로는 무엇인가 | 준비·실행·실패·재시도·운영 가정 | 관측 사용량과 추산 분리 |
| 무엇을 운영해야 하는가 | 필요한 로그·건강 상태·환경 전제 | 로컬 시작·실패 원인 추적 |
| 언제까지 무엇을 보여 줄 것인가 | 시간·범위·첫 기능·수용 기준 | 실제 시연할 흐름 |

미정 값은 미정으로 표시한다. 단순 실험에 가용성 SLO·온콜·다중 DB·복잡한 관측 스택을 강제하지 않는다.
3시간 구현이라면 첫 흐름, 실패 상태, 환경 재현과 그 흐름을 확인할 최소 근거를 우선 정한다.

## 선택과 변경 기록

중요한 선택은 [결정 템플릿](../assets/decision.md)에 배경·대안·이유·단점·재검토 조건을 남긴다.
상태는 proposed/accepted/deprecated/superseded 등 프로젝트가 정한 용어로 구분한다.
기존 결정을 바꾸면 이전 결정을 지우기보다 무엇이 바뀌었는지와 대체 자료를 연결한다.
사소한 함수명 선택마다 별도 ADR을 만들지 않는다.

가정은 결과와 구분한다. “빠를 것이다”를 측정으로 보고하지 않는다.
성능·복구·보안 요구가 검사 범위를 바꾸면 workflow의 checks/impacts와 수용 기준도 갱신한다.
