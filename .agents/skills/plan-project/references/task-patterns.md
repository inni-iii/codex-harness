# 작업 유형별 흐름

모든 작업은 필요한 입력 확인 → 수행 → 근거 대조 → 다음 작업 연결을 공유한다.
각 단계를 별도 파일이나 승인 절차로 만들 필요는 없다. 결과가 전제를 바꾸면 앞 단계로 돌아간다.
확인한 결함은 [검토·보완 반복](../../verify-work/references/follow-through.md)에 따라 같은 요청 안에서 재현·수정·회귀·최종 재검토까지 이어간다.
연구·설계의 반례도 재사용 가능한 시나리오로 남기고, 코드 결함은 실제 자동 회귀가 기본이다.

| 종류 | 시작 입력 | 핵심 수행 | 끝에서 확인할 것 |
|---|---|---|---|
| 연구 | 질문·제약·기존 결정 | 원문·대안·반증 비교 | 질문에 답하는가, 근거와 한계가 있는가 |
| 실험 | 가설·기준선·데이터·예산 | 통제된 비교·원본 보존 | 비교 조건·실패 포함 집계·재현 가능성 |
| 설계 | 목표·사용자 흐름·기존 계약 | 경계·선택지·상태·트레이드오프 | 구현 가능한가, 미결정이 표시됐는가 |
| 구현 | 수용 기준·기존 코드·계약 | 작은 기능을 끝까지 연결 | 요구 동작·오류·관련 회귀 |
| 디버깅 | 실제 증상·재현 조건 | 재현→원인 가설→좁은 수정 | 수정 전 재현, 수정 후 관련 회귀 |
| 리뷰 | 요청 범위·기준 코드·diff | 독립적인 요구/영향 대조 | 구체적 결함·재현·영향·근거 |

## 기능을 끝까지 연결하기

기능별로 사용자 동작, 요청·응답·오류, 업무 규칙·저장, 화면 상태, 확인 방법을 하나의 작업으로 묶는다.
백엔드 전체 → 프론트 전체 → 마지막 통합만으로 나누면 계약 문제가 늦게 드러난다.
작은 첫 흐름에서 이 경계를 연결하고, 이후 다른 기능을 같은 방식으로 확장한다.

예: “항목 생성”의 완료 기준을 다음처럼 관측 가능하게 적는다.

- 유효한 입력을 제출하면 새 항목이 표시되고 새로고침 후에도 유지된다.
- 잘못된 입력은 구체적 안내를 보여 주며 기존 입력을 보존한다.
- 연속 클릭의 동작은 합의한 중복 정책을 따른다.
- 기존 목록 조회·접근 권한이 유지된다.

실제 요구에 저장·권한이 없다면 위 예시를 의무 사항으로 가져오지 않는다.

## 3시간 제한에서의 구조

먼저 시연할 핵심 흐름과 실패 상태를 고르고, 실행·검증 방법을 일찍 확보한다.
외부 호출 경계와 변경하기 어려운 계약은 분리하되, 사용하지 않는 계층·관리 화면·범용 프레임워크는 만들지 않는다.
리팩터링은 관련 테스트를 보존하는 작은 단위로 한다. 기능 변경과 대규모 이동을 동시에 하지 않는다.
남은 부채는 영향·다음 수정 시점과 함께 기록한다. 완료를 위해 범위를 몰래 축소하지 않는다.

## task.json과 사람이 확인할 근거

task 명령은 목표·수용 기준을 가진 planned 기록을 만든다. 자동 작업 실행은 하지 않는다.
완료 기준에는 검증 방법과 실제 결과 위치를 연결한다.
파일 기록을 닫을 때는 [종류별 완료 기준과 명령](../../../../tools/harness/docs/completion.md)에 따라
실제 파일·해시·검사/실험 결과를 evidence ID에 연결하고 기준별 리뷰를 작성한다.
실행기는 누락·변조·오래된 결과를 확인한다. 내용의 진실성과 요구 충족은 리뷰에서 근거를 대조해 판단한다.
