# 작업 유형별 흐름

모든 작업은 필요한 입력 확인 → 수행 → 근거 대조 → 다음 작업 연결을 공유한다.
문서 기록은 필요한 만큼 유지하고, 단계별 검토 방식이면 각 단계의 결과를 보여준 뒤 사용자의 다음 지시를 기다린다. 결과가 전제를 바꾸면 관련 앞 단계로 돌아간다.
확인한 결함은 [검토·보완 반복](../../verify-work/references/follow-through.md)에 따라 같은 요청 안에서 재현·수정·회귀·최종 재검토까지 이어간다.
연구·설계의 반례도 재사용 가능한 시나리오로 남기고, 코드 결함은 실제 자동 회귀가 기본이다.

| 종류 | 시작 입력 | 핵심 수행 | 끝에서 확인할 것 |
|---|---|---|---|
| 연구 | 질문·제약·기존 결정 | 원문·대안·반증 비교 | 질문에 답하는가, 근거와 한계가 있는가 |
| 실험 | 가설·기준선·데이터·예산 | 통제된 비교·원본 보존 | 비교 조건·실패 포함 집계·재현 가능성 |
| 설계 | 목표·사용자 흐름·기존 계약 | 경계·선택지·상태·트레이드오프 | 구현 가능한가, 미결정이 표시됐는가 |
| 구현 | 수용 기준·기존 코드·계약 | 작은 기능을 끝까지 연결 | 요구 동작·오류·관련 회귀 |
| 디버깅 | 실제 증상·재현 조건 | 재현→원인 가설→좁은 수정 | 수정 전 재현, 수정 후 관련 회귀 |
| 리뷰 | 요청 범위·기준 코드·diff | 독립적인 요구/영향 대조 | 구체적 결함·재현·영향·근거 |

## 전체 작업의 8단계 체크리스트

요구사항 문서를 기준으로 프로젝트를 구현하는 요청의 전체 안내다. 기본은 단계별 검토이며 “이 문서로 구현해줘”라고 시작하면 1단계만 수행한다. 각 단계의 결과를 사용자가 직접 보고 다음 진행을 지시해야 넘어간다. 이 절차를 사용자가 매번 다시 적을 필요는 없다. 문서만 전달했으면 원하는 작업을 확인하고, 분석·계획·설계만 요청했으면 구현에 착수하지 않는다. 기존 작은 수정에 전체 프로젝트 절차를 강제하지 않는다.

- [ ] 1. 과제 설명과 기존 코드·실행 명령부터 확인한다.
- [ ] 2. 확정 요구, 가정, 미결정을 구분한다.
- [ ] 3. 모호한 조건은 제공된 담당자 대화 기능이 있으면 질문한다.
- [ ] 4. 필수 요구마다 확인 방법을 정한다.
- [ ] 5. 핵심 사용자 흐름을 먼저 작동시킨다.
- [ ] 6. 검증 실패는 원인과 근거를 확인해 수정한다.
- [ ] 7. 남은 시간을 보고 추가 기능과 검증 범위를 조정한다.
- [ ] 8. 완료·실패·미확인을 구분해 제출한다.

진행 방식: 한 단계씩 수행하고 결과를 보여준 뒤 멈춘다. 사용자가 다음 진행을 지시해야 넘어간다. 구현은 기능 묶음 단위로 진행하고, 검증 결과를 확인한 뒤 다음 작업을 선택한다.

출처와 읽지 못한 자료는 구분하고 중요한 미결정은 실제 답변으로 확인한다. 담당자 대화가 없으면 사용자에게 질문한다. 시간 제한이 없으면 임의 제한을 만들지 않고, 시간 부족을 이유로 필수 요구를 삭제하거나 미실행을 통과로 바꾸지 않는다. 제출은 현재 요청과 권한 범위에서 수행한다.

단계 끝에는 `현재 단계 / 수행 결과와 근거 / 미결정·미확인 / 다음 단계에서 할 일`을 짧게 보여주고 사용자 검토를 기다린다. 현재 대화에서 대상이 명확한 “다음 단계 진행해”, “확인했어, 다음” 같은 응답으로 이어간다. 수정 요청이면 현재 단계에서 보완하고 다시 결과를 보여준다. 결과를 보여준 사실·시간 경과·침묵을 다음 단계 승인으로 만들지 않는다. 단계별 새 task·문서·상태 저장소는 강제하지 않고 기존 정본과 task/notes/evidence를 재사용한다.

## 기능 묶음마다 다음 작업 판단

의미 있는 단계·기능 묶음 끝에는 [프로젝트 설명](project-explanation.md)의 관련 절에 구조·선택 이유·실패·검증 근거를 갱신하고 변경한 설명을 짧게 알린다. 중간 단계에는 예상 문답을 작성하지 않는다. 8단계 최종 정리에서 최종 코드·기록·검사 결과를 재대조한 뒤 같은 문서에 프로젝트별 문답과 알아야 할 개념을 모은다.

전체 요구와 공유 경계는 먼저 파악하되 이후 기능의 세부 설계를 미리 모두 고정하지 않는다. 기능 묶음은 사용자가 관측할 결과와 검사 가능한 경계로 정하고 파일·버튼 단위로 쪼개지 않는다.

`한 기능 구현(5) → 사용자 검토 → 기능 검증·수정(6) → 사용자 검토 → 다음 작업 제안(7) → 사용자 선택 → 다음 기능 또는 최종 정리`로 반복한다. 검증 실패면 범위 안에서 원인 확인·수정·관련 회귀를 수행하고 결과를 사용자에게 보여준다. 작은 편집마다 전체 검사/E2E를 반복하지 않고 유효한 기존 결과는 재사용한다. 새로운 중요한 요구 충돌·설계 변경·필수 환경 차단은 보고하고 그 의존 경로를 멈춘다. 단계별 모드에서는 미리 다음 단계의 독립 작업을 수행하지 않는다.

사용자가 “이후는 알아서 끝까지 진행해”처럼 명시적으로 자율 진행을 맡기면 그 범위에서만 `다음 기능 선택 → 필요한 상세 설계 → 구현 → 실제 실행·검증 → 요구/가정·잔여 갭 대조 → 수정 또는 다음 기능 선택`을 이어 수행한다. 중요한 미결정은 별도로 확인하고, 맡긴 범위 밖으로 확대하지 않는다. 더 나중의 단계별 검토 지시가 있으면 다시 매 단계 멈춘다.

이 절차는 현재 에이전트의 판단·수행 지침이다. context/flow가 사용자 응답을 자동 인증하거나 내용을 실행·승인하지 않는다. 새 훅·모델·별도 에이전트 팀을 시작하지 않으며 기존 권한·환경/보안·설계 준비 조건을 유지한다. 기록하는 flow에서 실제 선택 대기는 기존 user_choice 경로와 원문 근거를 사용하고, 그런 경로가 없으면 이동하지 않은 채 현재 단계에 머문다.

## 기능을 끝까지 연결하기

기능별로 사용자 동작, 요청·응답·오류, 업무 규칙·저장, 화면 상태, 확인 방법을 하나의 작업으로 묶는다.
백엔드 전체 → 프론트 전체 → 마지막 통합만으로 나누면 계약 문제가 늦게 드러난다.
작은 첫 흐름에서 이 경계를 연결하고, 이후 다른 기능을 같은 방식으로 확장한다.

예: “항목 생성”의 완료 기준을 다음처럼 관측 가능하게 적는다.

- 유효한 입력을 제출하면 새 항목이 표시되고 새로고침 후에도 유지된다.
- 잘못된 입력은 구체적 안내를 보여 주며 기존 입력을 보존한다.
- 연속 클릭의 동작은 합의한 중복 정책을 따른다.
- 기존 목록 조회·접근 권한이 유지된다.

실제 요구에 저장·권한이 없다면 위 예시를 의무 사항으로 가져오지 않는다.

## 3시간 제한에서의 구조

먼저 시연할 핵심 흐름과 실패 상태를 고르고, 실행·검증 방법을 일찍 확보한다.
외부 호출 경계와 변경하기 어려운 계약은 분리하되, 사용하지 않는 계층·관리 화면·범용 프레임워크는 만들지 않는다.
리팩터링은 관련 테스트를 보존하는 작은 단위로 한다. 기능 변경과 대규모 이동을 동시에 하지 않는다.
남은 부채는 영향·다음 수정 시점과 함께 기록한다. 완료를 위해 범위를 몰래 축소하지 않는다.

## task.json과 사람이 확인할 근거

task 명령은 목표·수용 기준을 가진 planned 기록을 만든다. 자동 작업 실행은 하지 않는다.
완료 기준에는 검증 방법과 실제 결과 위치를 연결한다.
파일 기록을 닫을 때는 [종류별 완료 기준과 명령](../../../../tools/harness/docs/completion.md)에 따라
실제 파일·해시·검사/실험 결과를 evidence ID에 연결하고 기준별 리뷰를 작성한다.
실행기는 누락·변조·오래된 결과를 확인한다. 내용의 진실성과 요구 충족은 리뷰에서 근거를 대조해 판단한다.
