# 실패와 정정을 재사용 규칙으로 만들기

반복되는 문제, 비자명한 해결, 사용자의 명시적인 정정에서 재사용할 지식을 정리할 때 읽는다.
[학습 기록 템플릿](../assets/lesson.md)을 사용하고, 작은 문구 수정·한 번의 외부 장애를 보편 규칙으로 만들지 않는다.
검토 상태·검색·범위·공유의 실행 절차는 [maintain-knowledge](../../maintain-knowledge/SKILL.md)와 [지식 CLI](../../../../tools/harness/docs/knowledge.md)에 연결한다.

## 기록에서 규칙까지

1. 실제 문제·원인·해결·근거를 원문과 날짜로 확인한다.
2. 이미 있는 지침·스킬·프로젝트 결정을 찾아 중복과 충돌을 확인한다.
3. 적용 조건과 적용하면 안 되는 조건을 정한다.
4. 해당 프로젝트의 notes/lessons 자료에 후보를 기록한다.
5. 확인한 결함을 수정하면 실패를 구분하는 재현/회귀 근거를 반드시 남긴다. 코드 결함은 자동 회귀가 기본이고, 연구·설계 오류나 자동화 불가는 시나리오·이유·수정 전/후 관측을 보존한다. 미실행은 통과로 기록하지 않는다.
6. 현재 작업 권한 안에서 지침을 보완하고, 언제 읽을지와 어떤 사례로 확인했는지 연결한다.

공통으로 만들 타당성이 부족하면 프로젝트 안에 둔다.
여러 프로젝트에서 반복됐다는 횟수만으로 전역 규칙으로 승격하지 않는다.
자기 평가 점수·모델의 confidence·사용자의 침묵을 사실 확인이나 채택 승인으로 쓰지 않는다.
현재 사용자가 승인한 범위에서 보완하고 개인 전역 설정은 변경하지 않는다.

## 기록할 상태

| 상태 | 의미 |
|---|---|
| candidate | 제안과 근거가 있으나 적용 범위/해결 검증이 남음 |
| evaluated | 적힌 사례에서 확인. 일반적인 우수성의 증명은 아님 |
| adopted | 해당 범위의 지침/문서에 반영하고 읽기 경로를 연결함 |
| superseded | 더 최근 결정으로 대체. 대체 자료·이유·날짜를 남김 |

상태는 문서 작성자가 근거와 함께 기록한다. 하네스가 진위를 자동 승인하지 않는다.

## 범용화 예

관측한 문제: 비동기 큐의 작업 수가 0이 되어도 consumer가 계속 기다려 처리 함수가 끝나지 않음.
원인: queue.join과 worker 종료를 동일한 것으로 가정함.
재사용할 판단: 배치 처리에는 생산 완료·처리 완료·worker 종료·취소/예외의 정리를 각각 확인한다.
적용 경계: 장기 실행 worker 서비스와 유한 배치의 종료 계약은 다르다.
확인할 사례: 빈 배치·정상 종료·처리 실패·취소·용량 초과. 수정 구현을 확인하기 전 해결 완료로 기록하지 않는다.

프로젝트의 DB 이름·교육 도메인·현재 노트북 경로는 이 규칙에 포함하지 않는다.

## 다음 작업에서 읽히게 하기

프로젝트에 남길 내용은 workflow.toml의 context.rules에 종류·주제·경로 조건과 문서 위치를 등록한다.
공통 스킬에 반영한 내용은 해당 SKILL.md와 .agents/context.toml의 조건에서 찾을 수 있게 한다.
구버전 규칙과 충돌하면 대체 상태와 우선순위를 명시하고 관련 원문을 추적 가능하게 유지한다.

원본의 관찰 hook·백그라운드 모델·전체 대화 수집·자동 전역 승격을 설치하지 않는다.
여기서는 사용 가능한 원문과 실제 작업 결과에서 필요한 규칙을 선별한다.

결함의 회귀 보존은 필수지만, 이를 모든 프로젝트의 공통 규칙으로 승격하는 것은 별도 판단이다.
[같은 요청 안의 후속 수행](../../verify-work/references/follow-through.md)과
[완료 기록](../../../../tools/harness/docs/review-rounds.md)을 연결한다.
