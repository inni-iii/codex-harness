# 작업하면서 이해를 기록하고 마지막에 문답 정리하기

프로젝트를 진행하며 사람이 전체 구조와 자신의 선택을 이해할 수 있는 설명을 유지한다.
의미 있는 프로젝트 작업에 적용하며 짧은 질문·작은 내부 편집마다 새 문서나 task를 강제하지 않는다.
기존 프로젝트 설명 문서가 있으면 재사용한다. 새 설명 문서의 기본 위치는
`docs/<프로젝트>/architecture/explanation-guide.md`이며 [양식](../assets/project-explanation.md.tmpl)을 필요한 만큼 채운다.
프로젝트가 아직 없으면 서비스 폴더를 임의 생성하지 말고 기존 작업 기록에 근거를 보존한다.

## 작업 중 기록

1. 요구·기존 코드에서 사용자 입력과 최종 결과, 처리 흐름·판단 규칙, 주요 컴포넌트의 책임을 설명한다.
2. 중요한 선택 직후 선택한 구조·알고리즘과 이유, 실제 검토한 대안·탈락 이유·포기한 조건·재검토 조건을 기록한다.
3. 기능 묶음 구현 후 실제 코드의 책임·저장 위치·데이터 수명·상태 변경·실패/복구를 해당 절에 반영한다.
4. 검사 후 입력·기대 결과·관측 결과·명령/cwd·대상 코드 상태·근거 위치와 보장 범위·미확인을 갱신한다.
5. 단계·세션 종료 때 바뀐 설명과 빠진 근거를 짧게 알리고, [기존 단계별 진행](task-patterns.md)의 사용자 검토를 유지한다.

작업 중에는 설명과 근거만 누적한다. 예상 질문·답변·꼬리질문은 최종 정리 때만 작성한다.
작은 수정마다 전체 문서를 다시 만들지 않고 영향받는 절을 갱신한다. 전체 대화나 로그를 복사하지 않는다.
작업의 진행/실패 이력은 task/notes, 요구·설계·검사 정본은 기존 소유 문서에 유지하고 여기서는 사람이 이해할 설명과 링크로 연결한다.
설명 문서가 작업 상태나 수용 기준의 별도 정본이 되지 않게 한다.

## 근거와 현재 상태

- 사용자 결정·AI 제안·코드 관측·실측을 구분한다. 선택 이유가 원문에 없으면 `선택 이유 미기록`으로 남긴다. 코드에서 추론한 이유는 추론으로 표시하고 당시 결정으로 꾸미지 않는다.
- 중요한 주장별로 `설계안 / 구현 확인 / 실행 확인 / 미확인 / 갱신 필요`를 필요한 만큼 표시한다. 코드가 있다는 것과 동작 검사를 실행했다는 것을 구분한다.
- 파일·함수/심볼·문서 절·결정 날짜·검사 보고서/로그와 대상 소스 상태를 연결한다. 줄 번호만으로 버전을 식별하지 않는다.
- 현재 동작과 요구 동작이 다르면 차이와 발견/후속을 연결한다. 요구를 코드에 맞춰 낮추거나 설명으로 결함을 감추지 않는다.
- 코드·요구·설계가 바뀌면 관련 설명과 이미 작성한 문답을 대조한다. 즉시 확인할 수 없는 주장은 `갱신 필요`로 두고 과거 실행 결과를 현재 결과로 쓰지 않는다.
- 중요한 결정 번복은 날짜·이전 선택·변경 근거를 짧게 남기고 실제 원문으로 연결한다. 개인 정보·비밀값·무관한 대화는 옮기지 않는다.

## 저장과 다시 읽기

실제 내용이 생길 때 한 문서를 생성하고 프로젝트/architecture 지도에 역할과 링크를 연결한다.
프로젝트 `workflow.toml`에 관련 코드 경로와 `project-explanation`, `final-explanation`, `resume`, `handoff` 주제로 읽을 조건을 등록한다.
규칙 예시는 문서가 실제로 존재한 뒤 프로젝트에 맞는 경로로 작성한다.

```toml
[[context.rules]]
topics = ["project-explanation", "final-explanation", "resume", "handoff"]
paths = ["src/core/**"]
documents = ["docs/example/architecture/explanation-guide.md"]
when = "현재 작업과 관련된 프로젝트 설명·결정·검증 근거를 확인"
```

조건은 OR이다. 예시 경로를 그대로 사용하지 말고 실제 관련 코드 범위로 바꾼다.
긴 설명 문서 전체를 필수 `context.documents`에 넣지 않는다. 작은 지도에서 현재 주제의 절과 원본만 읽는다.
세션 재개 때 현재 코드·결정·검사 상태와 관련 절을 대조하고 같은 경로를 이어 쓴다.
기능 문서 저장 명령이 공통 설명 문서도 자동 등록한다고 가정하지 않는다. 공통 문서의 지도/조건은 [문서 저장 계약](../../../../tools/harness/docs/project-documents.md)에 따라 함께 갱신한다.

## 최종 정리에서만 질문과 답변 작성

구현·검증이 마무리된 뒤 또는 사용자가 최종 정리를 요청한 범위에서 수행한다.
최종 코드의 진입점·호출자·핵심 처리·저장/상태 변경·오류 경계와 관련 테스트를 전체 흐름으로 다시 확인한다.
누적 설명·실제 결정 원문·검증 결과와 맞추고 미완료 기능은 미완료로 남긴다.

그 프로젝트의 실제 구조·중요 선택·한계에서 이해를 확인할 질문을 새로 도출한다.
고정 문제은행·제공받은 사례 문항의 원문/구체 내용·그 변형을 절차·양식·테스트·결과 문서에 저장하거나 재사용하지 않는다.
질문 수나 주제를 특정 서비스에 고정하지 않고 중복을 합친다. 단순 용어 확인뿐 아니라 실제 판단·흐름·대안·실패·검증의 범위를 설명할 질문을 고른다.
같은 설명 문서 끝에 다음 문항 형식으로 모은다.

- 질문과 짧은 핵심 답변
- 실제 처리 과정·선택 이유와 대안에서 포기한 것
- 보장하는 범위·보장하지 않는 범위와 미확인
- 확인할 코드·결정·테스트·실행 근거
- 알아야 할 개념의 쉬운 설명과 현재 구현에서의 역할
- 조건을 바꾼 꼬리질문과 답변 가능한 범위

일반적인 이상적 설계를 현재 구현의 답으로 쓰지 않는다. 근거가 부족하면 답변 공백과 필요한 확인을 표시한다.
구현 후 변경이 생기면 영향받는 문답을 `갱신 필요`로 두고 다음 최종 정리에서 재대조한다. 중간 단계마다 새 질문을 만들지 않는다.
사람이 이해했는지는 설명 생성과 별개다. 모의 문답은 요청된 경우 수행하며 작성만으로 이해 완료나 점수 향상을 주장하지 않는다.

## 확인 범위

선택/flow/링크 검사는 절차가 읽히고 원본에 도달하는지 확인한다. 문답의 정확성·실제 사용자 이해·평가 성적을 인증하지 않는다.
현재 에이전트가 기록·갱신·최종 문답을 수행한다. 이 참조는 자동 문서 생성기·백그라운드 훅·추가 모델 호출을 설치하지 않는다.
