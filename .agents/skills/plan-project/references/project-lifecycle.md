# 주제에서 설계·단계별 구현으로

새 주제·큰 기능의 처음부터 진행 순서를 잡거나, 설계 뒤 다음 구현 작업을 정할 때 읽는다.
단계를 위한 문서 세트를 모두 만들지 않는다. 현재 질문과 첫 사용자 흐름에 필요한 자료만 작성한다.

## 목표와 실행의 역할

기본은 사람이 정한 방향에서 작업을 도출하는 top-down이다. 사람은 Charter(목적·사용자·범위·제약), 중요한 아키텍처 경계·마일스톤·우선순위를 정하고 작업할 범위를 요청한다. AI는 초안·대안·미결정을 제안하고, 정해진 범위에서 요구·성공 조건·갭을 분석해 작업을 분해·배정하고 구현·검증한다.
이미 맡긴 범위의 세부 작업마다 새 요청/승인을 받지 않는다. 목표가 있다는 이유만으로 다음 마일스톤 전체를 착수하거나 외부 쓰기·다중 에이전트 실행 권한을 얻는 것은 아니다. 배정은 작업 단위·순서·담당 범위를 정하는 것이며 별도 에이전트 생성/모델 실행은 해당 권한과 실제 도구가 있을 때만 한다.

추론한 요구는 상위 목표의 어떤 부분에서 나왔는지 표시한다. 가능한 제품 선택이 여러 개라면 가정/제안으로 남기고, 결과를 바꾸는 미결정만 사람에게 묻는다. 중요한 목표·범위·아키텍처 경계·성공 조건을 AI가 완료하기 쉽게 바꾸지 않는다.

## 마일스톤에서 작업으로 연결

`Charter·아키텍처 경계 → 마일스톤 → 요구·성공 조건 → 현재 근거 → 갭 → 작업 → 검증 근거`를 연결한다.
여러 항목을 이어갈 때 M1/R1/G1 같은 안정된 식별자를 사용하고, 계획/근거의 날짜·버전을 남긴다. ID 자체가 지원되는 CLI 필드나 자동 실행 기능은 아니다.

- 마일스톤은 사용자/연구자가 얻을 결과와 달성 조건을 적는다. 파일 생성이나 작업 개수만으로 완료하지 않는다.
- 요구에는 부모 마일스톤, 관측 가능한 성공 조건과 확인 방법을 연결한다. 성능·보안·복구 등 해당 품질 조건도 포함한다.
- 갭은 성공 조건과 현재 확인된 상태의 차이다. 필요한 동작의 미구현, 구현했지만 미검증, 관측된 불충족, 의존성/환경 차단, 사람의 결정 대기를 구분한다. 코드나 근거를 보지 못한 상태를 미구현/충족으로 추정하지 않는다.
- 작업은 어떤 요구·갭을 해결할지, 선행 조건·입력 계약·수용 기준·확인 방법·담당 범위를 가진다. 미확인 갭에는 먼저 조사/검증 작업이 적합할 수 있다. 분해한 수용 기준이 상위 성공 조건을 빠뜨리지 않는지도 확인한다.

갭 평가는 확인 시점의 관측이다. 실제 task 진행 상태는 task.json, 실행 결과는 evidence 원본이 정본이다. 계획에 별도 task 완료 상태를 복사하거나 임의 진행률을 계산하지 않는다. 마일스톤 달성은 연결한 성공 조건과 현재에도 유효한 근거를 모아 판단하며 task가 모두 complete라는 이유만으로 선언하지 않는다.

| 단계 | 필요한 입력·결과 | 다음 단계로 갈 확인 |
|---|---|---|
| 주제·요구 | 문제·사용자·첫 흐름·제약·관측 가능한 성공 조건 | 목표/범위와 미결정이 구분됨 |
| 조사·실험 | 관련 원문·기존 코드·대안·필요한 실측 | 설계 선택에 필요한 근거/반례/한계가 있음 |
| 설계·결정 | 흐름·상태/오류·API/데이터·권한·품질 조건 | 첫 기능을 구현할 정도의 계약이 있고 미결정 영향이 명확함 |
| 구현 순서 | 사용자 기능 묶음·선행 작업·입력 계약·확인 방법 | 실행할 다음 작업과 시작 조건을 고를 수 있음 |
| 구현·검증 | 기능의 화면/API/저장·오류·정상 흐름과 관련 회귀 | 수용 기준·실제 근거·관련 보안/E2E를 대조함 |
| 다음 작업·재개 | 변경·실패·미결정·남은 작업과 원문 위치 | 다음 작업자가 현재 근거에서 이어갈 수 있음 |

절차 전체를 맡은 요청이면 에이전트가 필요한 단계를 이어 수행한다. 각 단계에 새 사용자 승인을 기본으로 추가하지 않는다.
설계만 요청받았다면 설계 범위를 지키고, 구현까지 요청받았다면 충분한 계약에서 다음 작업을 진행한다.
새 결과가 전제를 바꾸면 관련 설계·계획으로 돌아가 갱신한다.

## 문서와 상태 연결

프로젝트 생성 시 `brief.md`, `security.md`, `workflow.toml`, `index.md`가 생긴다. 설계나 코드가 완성된 상태는 아니다.
개요에는 Charter·아키텍처 경계·마일스톤과 결정의 정본 위치를, 인덱스에는 원문 위치와 읽을 조건을 둔다. 설계/계획이 필요해 실제 파일을 만들면 인덱스와 context 규칙에 연결한다.
작은 프로젝트는 개요 안에 계획을 적어도 된다. 커지면 [계획 양식](../assets/project-plan.md)으로 나누고 개요에서는 링크한다. 같은 요구·갭·상태를 두 곳에서 관리하지 않는다.
기존 task 형식은 유지한다. task.inputs에는 관련 계획/설계의 실제 파일을, notes에는 마일스톤·요구·갭과 task 수용 기준의 대응을 적는다. 계획 변경만으로 과거 수용 기준·complete 기록을 고쳐 쓰지 않는다.

계획에는 필요한 만큼 아래 관계를 적는다. 행의 상태는 실제 task.json/검증 근거로 돌아가 확인한다.

| 작업·상위 요구/갭 | 선행 작업·시작 조건 | 입력 계약 | 결과·완료 확인 | 다음 |
|---|---|---|---|---|
| 첫 사용자 흐름 / 관련 요구·갭 | 필요한 결정·외부 계약 확인 | 해당 설계·요구의 링크 | 정상·실패·저장/재조회 등 실제 결과 | 다음 사용자 흐름 |
| 다음 기능 / 관련 요구·갭 | 선행 결과가 현재 근거로 확인됨 | 재사용할 계약과 영향 범위 | 새 동작·기존 흐름 회귀 | 남은 기능 또는 인수인계 |

위 행은 제품 기능을 확정한 것이 아니다. 실제 프로젝트 작업명·task·근거 링크로 바꾼다.
`task.depends_on`은 관계 기록이다. 현재 실행기가 DAG 순서대로 구현하거나 선행 작업 완료를 자동 강제한다고 하지 않는다.

## 작업 시작 때 갭을 다시 재기

1. 현재 요청 범위와 관련 마일스톤·요구·성공 조건, 이전 갭 평가의 날짜/기준을 읽는다. 상위 목표가 없으면 요청 자체의 목표·수용 기준을 사용하고 가상의 프로젝트/마일스톤을 만들지 않는다.
2. 관련 코드·계약·선행 작업·실행 근거의 현재 유효성을 확인한다. complete 표지만으로 충족을 판단하지 않는다. 유효한 검증은 재사용하고 달라진 입력·의존성·새 불확실성에 필요한 확인만 수행한다.
3. 이전 갭과 비교해 해결됨·잔여·새로 발견됨·다시 열린 갭·미확인을 구분한다. 근거가 오래됐으면 현재 충족 여부를 미확인으로 남긴다. 과거 완료 이력은 보존한다. 첫 평가라면 기준선을 만든다.
4. 목표/성공 조건이 바뀌었으면 변경 결정·새 기준을 연결하고 이전 기준을 보존한다. 기준이 다른 갭을 단순 감소/증가나 진척률로 비교하지 않는다.
5. 요청 범위에서 시작 조건을 충족한 사용자 기능 묶음 또는 필요한 조사/검증을 선택한다. 관련 요구·갭, 선택 이유·선행 조건·담당 범위·수용 기준을 연결한다. 영향이 독립된 작업은 진행하고 공유 계약의 미결은 그 범위에 남긴다.

현재 요청을 막지 않는 다른 갭을 발견해도 자동으로 작업 범위를 넓히지 않는다. 요청과 목표가 충돌하면 영향과 선택지를 알리고, 사람이 명시적으로 정한 변경 목표를 계획에 반영한다. 짧은 질문·작은 수정은 관련 목표와 달라진 부분만 확인하며 전체 계획·테스트를 매번 다시 만들지 않는다.

## 수행 뒤 목표에 결과를 쌓기

관련 언어/보안/검증 스킬로 수용 기준을 검증한다. 백엔드 전체→프론트 전체→마지막 통합만으로 분해하지 않는다. 독립 작업 결과는 합친 상태에서도 검증한다.
작업 종료·중단 시 `해결한 요구/갭 → 실제 결과·근거 → 잔여/새 갭 → 다음 행동`을 notes에 남기고 계획의 관련 평가만 갱신한다. 과거 계획과 갭의 변경 이유·관측 시점은 짧은 변경 이력 또는 task notes로 보존한다. 성공 조건이 미확인이라면 구현 완료와 구분한다.

Bottom-up 발견은 관련 요구·갭에 연결한다. 상위 목표를 유지하는 수정은 요청 범위에서 처리하고, 신규 기능·주요 아키텍처 변경 등은 근거·대안·영향을 제안한다. 목표에 연결되지 않는 아이디어는 후속 후보로 남긴다. 긴급한 보안/회귀 문제는 숨기지 않고 현재 작업에 미치는 영향을 먼저 평가한다.
훅은 연결한 task와 기록 위치·누락을 보조 안내한다. 갭의 의미 판단·계획 갱신·자동 작업 할당을 훅이나 task.depends_on이 수행한다고 표현하지 않는다.

자료가 부족하면 필요한 원문/결정을 찾아 보완한다. 사용자 선택이 실제 결과를 바꿀 때만 질문하고, 결정 전에도 가능한 독립 작업은 계속한다.
세부 연결은 [워크플로 설정](workflow-setup.md), [작업 유형](task-patterns.md), [인수인계](handoff.md)를 따른다.

구체적인 코드/행동 변경의 분석·설계·정렬은 [REASONS 절차](reasons-canvas.md)를 따른다. 현재 준비 근거를 구현 flow에 연결하고, 작은 변경에는 기존 계약/경량 프로필을 재사용한다.
