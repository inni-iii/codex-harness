# 주제에서 설계·단계별 구현으로

새 주제·큰 기능의 처음부터 진행 순서를 잡거나, 설계 뒤 다음 구현 작업을 정할 때 읽는다.
단계를 위한 문서 세트를 모두 만들지 않는다. 현재 질문과 첫 사용자 흐름에 필요한 자료만 작성한다.

| 단계 | 필요한 입력·결과 | 다음 단계로 갈 확인 |
|---|---|---|
| 주제·요구 | 문제·사용자·첫 흐름·제약·관측 가능한 성공 조건 | 목표/범위와 미결정이 구분됨 |
| 조사·실험 | 관련 원문·기존 코드·대안·필요한 실측 | 설계 선택에 필요한 근거/반례/한계가 있음 |
| 설계·결정 | 흐름·상태/오류·API/데이터·권한·품질 조건 | 첫 기능을 구현할 정도의 계약이 있고 미결정 영향이 명확함 |
| 구현 순서 | 사용자 기능 묶음·선행 작업·입력 계약·확인 방법 | 실행할 다음 작업과 시작 조건을 고를 수 있음 |
| 구현·검증 | 기능의 화면/API/저장·오류·정상 흐름과 관련 회귀 | 수용 기준·실제 근거·관련 보안/E2E를 대조함 |
| 다음 작업·재개 | 변경·실패·미결정·남은 작업과 원문 위치 | 다음 작업자가 현재 근거에서 이어갈 수 있음 |

절차 전체를 맡은 요청이면 에이전트가 필요한 단계를 이어 수행한다. 각 단계에 새 사용자 승인을 기본으로 추가하지 않는다.
설계만 요청받았다면 설계 범위를 지키고, 구현까지 요청받았다면 충분한 계약에서 다음 작업을 진행한다.
새 결과가 전제를 바꾸면 관련 설계·계획으로 돌아가 갱신한다.

## 문서와 상태 연결

프로젝트 생성 시 `brief.md`, `security.md`, `workflow.toml`, `index.md`가 생긴다. 설계나 코드가 완성된 상태는 아니다.
개요에는 요구·결정을, 인덱스에는 원문 위치와 읽을 조건을 둔다. 설계/계획이 필요해 실제 파일을 만들면 인덱스와 context 규칙에 연결한다.
작은 프로젝트는 개요 안에 계획을 적어도 된다. 커지면 별도 구현 계획으로 나누되 같은 상태를 두 곳에서 관리하지 않는다.

계획에는 필요한 만큼 아래 관계를 적는다. 행의 상태는 실제 task.json/검증 근거로 돌아가 확인한다.

| 작업·순서 | 선행 작업·시작 조건 | 입력 계약 | 결과·완료 확인 | 다음 |
|---|---|---|---|---|
| 첫 사용자 흐름 | 필요한 결정·외부 계약 확인 | 해당 설계·요구의 링크 | 정상·실패·저장/재조회 등 실제 결과 | 다음 사용자 흐름 |
| 다음 기능 | 선행 결과가 현재 근거로 확인됨 | 재사용할 계약과 영향 범위 | 새 동작·기존 흐름 회귀 | 남은 기능 또는 인수인계 |

위 행은 제품 기능을 확정한 것이 아니다. 실제 프로젝트 작업명·task·근거 링크로 바꾼다.
`task.depends_on`은 관계 기록이다. 현재 실행기가 DAG 순서대로 구현하거나 선행 작업 완료를 자동 강제한다고 하지 않는다.

## 다음 작업을 고르기

1. 프로젝트 인덱스와 관련 요구·설계·계획의 필요한 부분을 읽는다.
2. 선행 작업의 task 상태뿐 아니라 현재에도 맞는 계약·증거·미결정을 확인한다. 오래된 complete 표지만으로 준비됐다고 판단하지 않는다.
3. 시작 조건을 충족한 다음 사용자 기능 묶음을 선택한다. 영향이 독립된 작업은 진행하고 공유 계약의 미결은 그 범위에 남긴다.
4. 수용 기준·검증 범위를 정하고 관련 언어/보안/검증 스킬로 수행한다. 백엔드 전체→프론트 전체→마지막 통합만으로 분해하지 않는다.
5. 결과와 실제 검사를 task/evidence에 연결하고 필요한 설계·인덱스·다음 작업을 갱신한다. 독립 작업 결과는 합친 상태에서도 검증한다.

자료가 부족하면 필요한 원문/결정을 찾아 보완한다. 사용자 선택이 실제 결과를 바꿀 때만 질문하고, 결정 전에도 가능한 독립 작업은 계속한다.
세부 연결은 [워크플로 설정](workflow-setup.md), [작업 유형](task-patterns.md), [인수인계](handoff.md)를 따른다.
