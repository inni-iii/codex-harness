# 세션 격리와 통합 검토

여러 세션이 같은 레포를 수정하거나 독립 작업을 합칠 때 읽는다.
세션별 Git worktree를 사용하고 이미 격리된 작업이면 그 공간을 재사용한다. 메인 체크아웃의 브랜치를 다른 세션 작업 중 전환하지 않는다.
같은 함수를 계속 공동 수정해야 하는 작업은 한 세션이 쓰기를 맡고 다른 세션은 제안·검토를 담당하도록 조정한다.
분리한 포트·DB/데이터·브라우저 프로필·의존성도 확인한다. 작업 폴더 격리만으로 실행 환경 전체가 분리되지는 않는다.

## 진행 중인 다른 세션의 변경 구분

새 파일·미등록 스킬·임시 링크 오류를 발견하면 현재 사용자 설명, 작업 기록과 이전 기준 상태를 확인한다.
사용자가 다른 세션의 담당 범위를 이미 알려줬으면 그 정보를 재사용한다. 파일의 이름·수정 시각만으로 소유자나 완료 상태를 확정하지 않는다.

| 상태 | 처리 |
|---|---|
| 확인된 다른 세션의 진행 중 변경 | 담당 범위를 보존하고 중간 상태로 기록. 임의 등록·완성·삭제하지 않음 |
| 다른 세션이 완료한 변경의 결함 | 근거와 영향 범위를 확인해 보완/통합 판단으로 연결 |
| 내 변경의 회귀 | 현재 요청 범위에서 수정하고 관련 검사를 다시 수행 |
| 소유·완료 여부 미확인 | 관련 원문·작업 기록을 더 확인. 타인 작업으로도 완성 결함으로도 단정하지 않음 |

예: 다른 세션이 새 스킬을 만드는 중이라 참조/등록이 잠시 빠졌다면 구성 검사 결과 자체는 실패로 남기되, 해당 작업의 진행 중 상태로 분류한다.
무관한 내 작업은 관련 원문과 검사로 이어간다. context 전체 검증이 막히면 필요한 지침을 직접 읽는 fallback을 사용한다.
현재 작업이 그 스킬·공유 설정에 의존하면 그 범위는 미확인으로 남긴다. 검사를 무시하거나 전체 레포가 통과했다고 보고하지 않는다.
담당 작업이 완료되거나 실제 통합할 때는 최신 파일·등록·참조·의존 관계를 다시 읽고 결합 상태를 검증한다.
실행 전후 상태가 바뀌어 stale인 결과를 현재 상태의 통과로 재사용하지 않는다.

## 보안 검토와 구현을 병행할 때

프로젝트 active는 실제 검사 명령을 사용할 준비이고 보안 완료 승인이 아니다.
세션 A의 검토 대기 때문에 세션 B의 구현·로컬 검사를 모두 멈추지 않는다.
예를 들어 A가 인증 정책을 보완하고 B가 독립적인 표시 화면을 구현하면, 인증의 pending 경로와 공유 계약·소비자를 명시하고 B는 자기 범위의 검사를 진행한다.
관련 경계가 미정인 작업은 합의된 인터페이스·합성 데이터로 구현할 수 있지만, 인증 우회나 실제 비밀값·실데이터 사용으로 임시 연결하지 않는다.
완성하지 않은 경계를 실제 사용 가능한 기능으로 보고하지 않는다.

보안 프로필의 상태·영향 경로·종료 코드는 [프로젝트 명세](../../../../tools/harness/docs/project-workflows.md)의 “동시 작업의 미결 범위와 완료 판정”을 따른다.
검토 문서 전체의 초안·해시 불일치는 범위를 확정할 근거가 없으므로 전체 미결이다. 독립 작업은 검토한 기준 문서를 가진 각 worktree에서 이어가고, 변경한 문서는 통합할 때 다시 검토한다.
공유 인증 계약에 의존하는 화면은 독립 작업으로 취급하지 않는다. 경로 규칙과 impacts에 실제 의존 관계를 포함한다.

검사 도중 다른 세션이 원본을 편집해야 하면 `check --snapshot`으로 고정 사본을 검사할 수 있다.
이는 검사 입력을 고정하며 편집 작업·포트·DB를 격리하는 worktree를 대신하지 않는다.
Git 첫 커밋이 없어 worktree를 만들 수 없는 상태에서도 사용할 수 있지만, 동일 파일의 동시 쓰기는 계속 담당자를 나눈다.
사본 검사 뒤 원본이 바뀌면 그 결과는 당시 사본의 근거다. 통합·완료 시 현재 소스·환경과 일치하는 근거를 사용한다.
실행 제약·의존성과 비밀값 처리·재사용 조건은 [검증 명세](../../../../tools/harness/docs/verification.md)를 따른다.

## 변경을 합칠 때

각 작업의 목표·기준 커밋·양쪽 변경·테스트 근거를 읽는다. 상대 변경이 있다는 이유만으로 덮어쓰거나 버리지 않는다.
공통 원본·target·source를 비교하고 각 변경의 최종 처리와 이유를 기록한다.
겹친 줄뿐 아니라 호출자·API·권한·상태·설정의 의미 충돌도 찾는다. 한쪽 테스트가 통과했다는 사실로 다른 쪽 요구를 지우지 않는다.
양쪽 요구를 함께 충족할 수 있으면 결합하고 관련 회귀를 확인한다. 요구·근거로 명확히 판단되는 기술적 충돌은 해결하고 이유를 보고한다.
유효한 두 요구가 양립하지 않거나 제품 정책·설계 선택이 필요한 경우에는 결정 전에 양쪽 의도·충돌 이유·선택별 영향·추천안을 사용자에게 알린다.
조합을 검토하는 동안 입력이 바뀌면 이전 결론과 검증을 현재 상태에 맞게 다시 확인한다.

[세션·통합 도구](../../../../tools/harness/docs/sessions.md)는 격리 공간·중복 경로·텍스트 충돌·통합 검사를 지원한다.
review.md의 변경 의도·공유 경계·수용 기준 검토는 에이전트가 수행한다. 기계 검사 성공을 자동 설계 합의로 표현하지 않는다.
다른 세션에 자동으로 메시지를 보내거나 모든 세션을 감시하는 기능은 없다. 실제 통합/인수인계 시 최신 상태를 확인한다.
원격 서버는 계속 읽기 전용이며, 이 절차가 원격 쓰기나 배포 권한을 주지 않는다.
