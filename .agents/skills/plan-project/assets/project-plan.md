# 목표·갭과 작업 계획

관련 마일스톤을 여러 작업/세션으로 이어갈 때 프로젝트의 기존 계획에 필요한 절만 옮긴다.
작으면 brief 안에서 관리한다. 이 양식은 계획 정본을 나눌 때의 대안이며 별도 문서 생성을 강제하지 않는다.
아래 행은 작성 예시다. 실제 요구·관측·task·근거로 바꾸며 현재 구현이나 완료를 뜻하지 않는다.

## 상위 기준

- Charter·아키텍처 경계의 정본 위치와 기준 날짜/버전:
- 대상 마일스톤 ID·정본 위치·달성 조건:
- 이번 사람이 요청한 실행 범위·제외 범위:
- 마지막 갭 평가 시점·코드/계약 기준·검증 환경:
- 목표·성공 조건이 달라졌다면 변경 결정·이전 기준의 위치:

상위 목표를 여기 복제하지 않는다. 사람이 결정한 내용, AI 제안/가정, 미결정을 구분한다.

## 요구와 성공 조건

| 요구 ID | 부모 마일스톤 | 요구·출처/결정 | 관측 가능한 성공 조건 | 확인 방법·환경 |
|---|---|---|---|---|
| R1 | M1 | 실제로 제공할 결과와 그 근거 | 사용자가 얻을 결과·필요한 오류/품질 조건 | 결과를 판정할 관측/검사 |

## 현재 갭 평가

| 갭 ID·관련 요구 | 현재 관측·근거/확인 시점 | 남은 차이와 구분 | 이전 평가 대비 변화·이유 | 연결할 작업·시작 조건 |
|---|---|---|---|---|
| G1 / R1 | 코드·계약·실행/검토 근거의 위치; 모르면 미확인 | 미구현 / 미검증 / 관측된 불충족 / 차단 / 결정 대기 / 충족 | 해결·잔여·신규·다시 열림·미확인 또는 첫 기준선 | 실제 task 위치 또는 필요한 조사/검증 |

이 표는 시점별 요구 충족 평가다. task의 진행 상태와 실행 결과는 task.json/evidence 원본에서 확인한다.
과거 complete나 파일 존재만으로 충족을 표시하지 않는다. 다른 기준의 평가를 진척률로 직접 비교하지 않는다.

## 실행할 작업

| 작업·task 위치 | 해결할 요구/갭 | 선택 이유·선행 작업·입력 계약 | 담당 범위 | task 수용 기준과 상위 성공 조건의 대응·검증 |
|---|---|---|---|---|
| 실제 작업 또는 계획 후보 | R1 / G1 | 요청 범위에서 우선할 이유·시작 조건 | 자기 작업 또는 허가된 담당자·공유 경계 | 빠진 성공 조건이 없는지와 확인 방법 |

task.inputs에는 실제 계획/설계 파일 경로를 연결하고 notes에 ID·수용 기준 대응을 적는다.
task.depends_on은 기존 관계 기록으로 사용한다. 임의 JSON 필드·자동 배정기·실행 DAG를 추가하지 않는다.
완료 표를 따로 복제하지 않는다. 필요한 마일스톤 달성 평가는 성공 조건별 유효한 근거를 모아 판단한다.

## 평가 변경과 다음 행동

- 이전 평가/당시 관측의 위치:
- 이번 결과로 줄어든 갭·실제 근거:
- 남은/새 갭·영향·미확인과 필요한 결정:
- 목표/경계 변경 제안 또는 범위 밖 bottom-up 발견·후속 위치:
- 다음 요청에서 시작할 작업 후보·시작 조건:

작업 전후 차이·실패 원인은 task notes에 남기고 여기서는 링크할 수 있다. 긴 이력을 매번 복사하지 않는다.
현재 관측·요구·근거를 지우거나 성공 조건을 약화해 완료로 만들지 않는다.
