# 프로젝트 개요

상태: 미정 항목은 미정으로 유지한다. 이 템플릿 자체는 제품 결정이 아니다.

- 주제와 해결할 문제:
- 대상 사용자와 핵심 시나리오:
- 성공 조건과 시연할 흐름:
- 작업 시간·비용·환경 제약:
- 포함 범위와 제외 범위:
- Charter의 기준 날짜/버전·중요 변경 결정의 위치:
- 사람이 정한 아키텍처 경계·고정 제약과 AI 제안/미결정의 구분:
- 마일스톤 ID·사용자/연구 결과·달성 조건·우선순위:
- 합의된 기술: Svelte 프론트, Python 백엔드, PostgreSQL
- 선택할 기술: 프레임워크·PostgreSQL 버전/driver/ORM/migration 도구/확장·인증·배포·API 클라이언트 생성 도구
- 디자인 기준의 위치와 승인 상태:
- 기존 자료·코드·과거 실패의 위치:
- 미해결 질문:
- 첫 기능과 확인 방법:
- 필요 시 설계·구현 계획의 위치(선행 작업·입력 계약·산출물·완료 근거·다음 작업):
- 요구·성공 조건·현재 근거·갭·작업 연결의 정본 위치(작으면 이 개요, 나누면 계획 링크만):
- 첫 갭 평가의 기준/시점·미구현/미검증/차단/결정 대기와 관련 근거:
- 현재 단계와 다음 작업의 원문 위치(실제 상태는 task/evidence 참조):
- 관련 있는 품질 기준: 성능·입력/동시성·데이터 손실/복구·접근 권한·비용·오류 추적
- 결정의 상태·대안·기각 이유·재검토 조건을 남길 위치:
- 인수인계·프로젝트 학습 기록의 위치와 읽기 조건:

프로젝트가 정해지면 `docs/projects/<이름>/brief.md` 등 프로젝트별 위치로 복사한다.
비밀값·개인 인증 자료는 넣지 않는다.
계획을 나누면 plan-project의 목표·갭 계획 양식에서 필요한 절만 사용한다. Charter·아키텍처·마일스톤을 각각 별도 파일로 만들 필요는 없다. 목표와 실제 작업 상태·검증 결과를 중복 관리하지 않는다.

코드/행동 변경의 설계 정본에는 필요한 REASONS 관점과 R/O·허용 변경 위치·미결정을 연결한다. 작으면 이 개요의 설계 절을 사용하고, 실행 시에는 현재 설계/정렬 근거를 task/evidence로 묶는다.
