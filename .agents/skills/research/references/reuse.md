# 기존 해결책을 재사용할지 판단하기

새 공통 도구·의존성·MCP·추상화를 도입하기 전에 읽는다.

## 검색 순서와 중단 조건

- 먼저 레포의 manifest, 공개 함수, 유사 기능, 테스트, 실패 기록을 rg로 확인한다.
- 정확한 기능명뿐 아니라 코드에서 발견한 별칭·타입·호출 경로도 검색한다.
- 필요가 남으면 해당 언어의 패키지 저장소, 공식 문서·소스, 유지되는 구현을 비교한다.
- 도구가 이미 연결되어 있으면 실제 기능·입출력·권한을 확인한다. MCP가 존재한다는 이유만으로 설치하지 않는다.
- 요구를 만족하는 후보와 유지 비용이 확인되면 무관한 후보까지 계속 수집하지 않는다.
- 검색에서 찾지 못한 것과 존재하지 않는 것을 구분한다. 조사 범위를 적는다.

| 선택 | 적합한 경우 | 반드시 비교할 비용 |
|---|---|---|
| 기존 구현 유지 | 요구를 이미 충족 | 실제 남은 결함과 우회 비용 |
| 그대로 채택 | 공개 계약이 요구와 맞음 | 라이선스·버전·전이 의존성·설치 재현성 |
| 얇게 확장 | 몇 가지 경계만 다름 | 래퍼가 API를 숨겨 업그레이드를 어렵게 하는지 |
| 직접 구현 | 규칙이 작거나 후보가 부적합 | 검증·보안·장기 유지 비용 |

## 다른 레포의 스킬을 가져올 때

SKILL.md의 제목만 읽고 이식하지 않는다. 전체 본문과 사용할 참조·스크립트를 읽고 호출 관계를 확인한다.
원본의 제품명·DB·개인 경로·권한·모델·강제 승인·고정 커버리지 기준을 분리한다.
스크립트는 종료 코드, shell 파이프, 삭제·설치·업로드, 로그의 비밀 노출, 캐시·상태 변경을 검토한다.
일반화할 판단·실패 조건·작은 예제를 재작성하고, 출처·읽은 범위·채택·제외·수정 이유를 남긴다.
라이선스가 불명확한 외부 코드·문서는 대량 복사하지 않는다.

예: API 테스트의 fixture라는 개념은 재사용할 수 있다. 원본의 운영 DB 이름을 문자열 치환해 테스트 DB를 선택하는 코드는 가져오지 않는다.
