# 근거를 판정하는 절차

기술 선택·성능 주장·지원 여부처럼 결론을 바꾸는 내용을 조사할 때 읽는다.

## 질문을 비교 가능하게 만들기

“가장 좋은 X”를 바로 순위로 바꾸지 않는다. 필요한 기능, 환경, 데이터 규모, 기존 자산, 시간·비용, 변경 가능성을 적는다.
현재 요구에 없는 고가용성·멀티테넌트·GPU 배포를 임의 조건으로 추가하지 않는다.
비교 기준은 결과를 본 뒤 유리하게 바꾸지 않는다. 바꾸어야 하면 이유와 이전 기준을 남긴다.

## 주장 장부

결정에 중요한 주장만 다음 형태로 기록한다. 간단한 조회에는 답과 출처 한 개로 충분하다.

| 주장 | 원문·확인일 | 정확한 버전/변종·환경 | 문서상/실측/추론 | 반증·한계 |
|---|---|---|---|---|
| 후보가 필요한 플랫폼을 지원 | 공식 지원표·날짜 | OS·아키텍처·런타임 | 문서상 지원 | 실제 설치는 미확인 |
| 후보가 더 빠름 | 원본 벤치·날짜 | 입력·동시성·하드웨어 | 타인 실측 | 우리 부하와 다름 |

- 검색 결과 요약에서 끝내지 말고 주장한 원문 구간을 읽는다.
- 같은 발표를 재인용한 블로그 여러 개를 독립 근거로 세지 않는다.
- 공식 문서는 API 계약·지원 범위에 강하다. 실제 품질·안정성은 재현 코드·실측·공개 결함도 대조한다.
- 두 근거가 충돌하면 버전·날짜·변종·입력 조건부터 맞춘다. 비교 불가능하면 수치 하나로 합치지 않는다.
- GitHub의 closed 표시만으로 수정됐다고 하지 않는다. 수정 PR·merge·출시 버전과 사용 버전을 확인한다.
- 모델 가중치, 서버 도구, 데이터·폰트·아이콘은 각각의 라이선스 범위를 확인한다.
- 접근 불가 원문은 미확인으로 적는다. 읽지 않은 문서를 출처로 사용하지 않는다.

## 반증과 선택

1. 현재 선호 후보가 실패하는 조건·이슈를 찾는다.
2. 기존 구현 유지, 작은 자체 구현, 다른 후보 중 가장 강한 대안을 같은 기준으로 비교한다.
3. 우리 조건에서 확인 가능한 작은 실험을 제안하거나 권한 안에서 수행한다.
4. 채택안·탈락안 각각에 이유를 남긴다. “지금 환경에서 불가”를 영구적인 제품 한계로 일반화하지 않는다.

출력은 추천 하나와 성립 조건, 차선책이 유리한 조건, 결론을 바꿀 가장 큰 불확실성을 포함한다.
사실·판단·사용자 채택 결정을 구분하고 실제 합의·실험을 꾸며 쓰지 않는다.
