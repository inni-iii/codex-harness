# 위협 모델과 보안 설계

새 서비스, 권한/데이터 모델 변경, 업로드·외부 호출·실행 도구 도입에 사용한다.
기존 작은 변경은 이미 작성한 모델에서 바뀐 경계만 갱신한다.
보안 설계는 배포 직전의 별도 감사가 아니라 구현할 계약을 정하는 일이다.

## 실제 흐름에서 시작

프로젝트의 brief·API 계약·코드·잠금 파일을 확인하고 [프로젝트 양식](../assets/security-profile.md)에 다음 사실을 기록한다.

| 항목 | 정할 내용 | 피할 오류 |
|---|---|---|
| 보호 자원 | 사용자 콘텐츠, 세션, 로컬 파일, 외부 API 키, 비용·실행 권한 | 모든 데이터를 같은 민감도로 취급 |
| 주체 | 비로그인, 본인, 타 사용자, 운영자, 외부 제공자, 모델/도구 | 로그인했다는 이유로 모든 자원 허용 |
| 진입점 | API, 폼, URL, 파일, webhook, MCP 결과, 저장된 콘텐츠 | 브라우저 입력만 비신뢰로 간주 |
| 신뢰 경계 | 브라우저↔서버, 사용자 A↔B, 앱↔제공자, 데이터↔명령 | 같은 프로세스 안이면 같은 신뢰라고 가정 |
| 결정 위치 | 실제 데이터 읽기/쓰기·외부 요청 직전의 서버/실행기 | UI 버튼·프롬프트의 금지 문구로 대신 |
| 자원 한도 | 본문/파일 크기, 시간, 동시성, 재시도, 비용·저장량 | 값만 정하고 어디서 제한하는지 생략 |
| 실패 정책 | 거부 응답, 부분 결과 폐기, 롤백, 중복 처리 | 오류 때 권한 생략·다른 도구로 우회 |

개인 키나 실제 사용자 자료를 양식에 넣지 않는다. 비밀값은 이름·보관 방식·접근 주체만 기록한다.
데이터 흐름은 “사용자→POST /items→인증→자원 권한→저장→응답”처럼 실제 경로로 작성한다.
DB는 PostgreSQL을 사용한다. 프레임워크·DB 버전/확장·인증 제공자는 프로젝트 결정이며 이 문서가 자동 선택하지 않는다.

## 공격 시나리오를 검증 가능한 조건으로 바꾼다

각 중요한 흐름에 다음을 연결한다.

1. 공격자가 가진 접근과 모르는 정보를 적는다. 인터넷 전체 접근이나 관리자 권한을 임의 가정하지 않는다.
2. 공격자가 바꿀 수 있는 입력을 고른다. URL의 ID, body의 owner_id, 파일 이름, 도구가 반환한 URL/명령 등이 후보이다.
3. 입력이 닿는 자원과 피해를 적는다. “보안 위험” 대신 타 사용자 데이터 유출, 임의 파일 덮어쓰기, 중복 과금처럼 쓴다.
4. 막아야 하는 조건과 서버 측 방어를 정한다. 권한 확인은 실제 대상 자원에 결합하고, 실패 시 처리 전 거부한다.
5. 정상 대조군과 공격 사례, 관측할 상태·부작용, 실행할 테스트를 연결한다.

예: 문서 조회에서는 A의 정상 조회, B가 A의 ID로 직접 호출, 미인증 호출, 삭제/권한 변경 후 재조회가 관련될 수 있다.
수정·첨부 다운로드·검색 결과·export도 같은 권한 경계를 우회하지 않는지 본다.
추측하기 어려운 ID, 프론트 필터링, 암호화만으로 요청별 권한 검사를 대체하지 않는다.

## 위험과 미결정 처리

심각도는 접근 전제·재현 가능성·노출 데이터·행동 범위·복구 가능성을 근거로 정한다.
스캐너의 CVSS나 모델의 확신을 그대로 제품의 심각도로 복사하지 않는다.
악용이 확인되지 않은 후보도 중요한 경계면 조사 대상으로 남기되 확인된 취약점과 구분한다.

보안 판단이 필요한 미정 항목에는 영향과 임시 제한을 적는다. 예를 들어 공유 권한이 미정이면 모든 문서를 공개하는 임시 구현을 두지 않는다.
현재 승인 범위 안에서 안전한 기본 동작으로 구현하고, 실제 제품 동작을 바꾸는 결정을 확인한다.
모든 단계마다 별도 승인을 반복하지 않는다. 문서를 채우는 것으로 권한·인증이 구현됐다고 하지 않는다.

새 입력, 역할, 저장소, 외부 제공자, 패키지 실행 권한, 모델 도구가 추가되면 해당 흐름의 모델과 테스트를 갱신한다.
