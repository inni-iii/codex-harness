# 애플리케이션 구현과 보안 검토

입력→자원 접근→출력의 실제 처리 경로를 읽고 변경과 관련된 항목을 선택한다.
아래 항목 전체를 모든 수정에 강제하거나 코드 예제를 프로젝트 사실로 취급하지 않는다.

## 인증·세션·자원 권한

서버에서 검증한 인증 정보에서 주체를 얻는다. body/query의 user_id·role·tenant_id를 주체의 권한 증거로 삼지 않는다.
토큰의 서명·발급자·수신 대상·만료 등은 선택한 인증 방식과 라이브러리의 계약대로 확인한다. JWT를 decode만 한 상태는 검증된 인증이 아니다.
비밀번호가 필요한 서비스에서는 유지되는 검증 라이브러리의 적절한 비밀번호 해시를 사용하고 직접 암호 방식을 설계하지 않는다.

조회·수정·삭제·다운로드·목록·검색·export·실시간 채널 각각에서 대상 자원의 소유/조직/역할 조건을 확인한다.
허용 필드는 명시적으로 제한해 요청 body의 owner·admin·가격·상태 변경을 무제한 반영하지 않는다.
캐시 키와 SSR 상태에 사용자/조직 경계를 반영하고 사용자별 상태를 전역 공유하지 않는다.
권한 변경·세션 폐기와 진행 중 요청의 관계도 정한다. 보안상 중요한 쓰기는 실제 실행 시점에도 조건을 유지한다.

미인증·다른 사용자·권한 없는 역할·만료/폐기 토큰을 서버 직접 요청으로 확인한다.
오류 코드만 보지 않고 데이터·외부 호출이 바뀌지 않았는지도 확인한다.
관련 기준: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## 파싱·저장·명령 실행

schema의 타입·길이·깊이·배열 수·열거값과 업무 제약을 함께 검사한다. 중복 키·알 수 없는 필드·null과 누락을 어떻게 취급할지 정한다.
오류 응답은 안정된 코드와 필요한 최소 설명으로 내보내고 원본 본문·stack trace·DB 연결 정보는 노출하지 않는다.
DB 값은 매개변수로 전달한다. 정렬 필드·컬럼명처럼 매개변수화할 수 없는 식별자는 승인한 값으로 매핑한다.
프로세스 호출은 검토한 실행 파일과 argv를 사용한다. argv 분리만으로 옵션 주입까지 막히지는 않으므로 선행 '-'와 사용자 제어 옵션도 검사한다.
데이터를 eval·exec·shell 또는 위험한 객체 역직렬화로 해석하지 않는다.

파일 경로는 승인된 루트와 정규화된 실제 경로의 포함 관계를 확인한다. 문자열 접두사만 비교하지 않는다.
상대 경로의 '..', 절대 경로, URL 인코딩, 심볼릭 링크, 기존 파일 덮어쓰기·경합을 사용 방식에 맞춰 다룬다.
동시 공격자가 파일을 바꿀 수 있는 환경에서는 사전 resolve만으로 끝내지 않고 안전한 파일 열기·디렉터리 권한까지 검토한다.

## 파일·압축·외부 URL

파일의 이름·확장자·Content-Type은 사용자가 조작할 수 있다. 서버에서 필요한 실제 형식과 크기를 검사한다.
업로드 스트림·변환·압축 해제에 바이트·항목 수·해제 후 크기·시간 한도를 둔다. 이름을 서버가 생성하고 실행 가능한 위치와 분리한다.
다운로드·미리보기에도 자원 권한과 안전한 응답 Content-Type/Disposition을 적용한다.
HTML/SVG처럼 능동 콘텐츠를 제공한다면 출력 origin과 정화 정책을 별도로 정한다.
참고: [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

사용자나 도구의 URL을 서버에서 조회한다면 목적지·포트·프로토콜·이름 해석·리다이렉트별 허용 정책을 둔다.
loopback·사설/링크 로컬·메타데이터 주소·IPv6·대체 IP 표기와 DNS 재해석을 고려한다.
문자열 정규식으로 끝내지 않고 실제 연결 경로와 네트워크 통제를 함께 사용한다. 테스트에서는 실제 내부 주소에 요청하지 말고 격리된 resolver/transport로 차단을 관측한다.
참고: [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

## 브라우저와 요청 위조

일반 텍스트는 해당 출력 맥락에서 인코딩한다. Svelte의 {@html} 등 원문 HTML 경로는 필요성과 유지되는 정화 정책을 확인한다.
URL 스킴·HTML 속성·CSS·스크립트 맥락은 서로 다른 검증을 필요로 한다. 서버 검증도 유지한다.
쿠키·CORS·CSRF·CSP는 인증 전달·origin·외부 로그인·SSR 구조에 맞춰 정한다.
모든 서비스에 SameSite=Strict를 복사하거나 CSP unsafe-inline/unsafe-eval을 기본 허용하지 않는다.
CORS는 자원 권한 검사를 대신하지 않으며 쿠키 인증의 상태 변경 요청은 CSRF 경계를 별도로 검토한다.

## 중복·외부 이벤트·비밀값·로그

생성·권한 변경·결제 등에는 중복 키의 범위와 보존, 동시 요청의 원자성, 실패 후 재시도 조건을 정한다.
webhook은 제공자의 **현재 공식 규격**에서 원본 본문·서명 방식·헤더·시간·재전송 방지를 확인한다. 다른 서비스의 예제 헤더/HMAC 코드를 복제하지 않는다.
서명 검증에 실패하거나 시간 범위를 벗어나면 부작용을 일으키지 않는다. 유효 이벤트도 중복 처리 방지가 필요하다.

비밀값은 클라이언트 번들·공유 문서·명령 인자·로그·trace에 넣지 않는다. 공개 가능한 설정과 서버 전용 값을 구분한다.
로그는 이벤트·안전한 상관 ID·단계·결과 코드 중심으로 구성하고 원본 토큰·쿠키·파일 본문·전체 모델 응답을 기본 기록하지 않는다.
예외 경로와 디버그 출력에도 같은 기준을 적용하고, 합성 비밀값을 넣어 노출되지 않는지 확인한다.
실제 값이 노출되면 유효성을 시험하지 않고 사용 중단·교체 필요와 위치만 알린다. 삭제만으로 이미 노출된 값이 안전해지지 않는다.
