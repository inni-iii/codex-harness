# 구현·결정과 문서 맞추기

기능·API·CLI·설정·릴리스의 설명이 실제 상태와 맞는지 확인하거나 문서를 최신화할 때 읽는다.
코드가 현재 어떻게 동작하는지와 제품이 어떻게 동작해야 하는지를 각각 확인한다.

## 기준과 권위 구분

- 현재 요청이 특정 주제·브랜치 diff·릴리스 버전·전체 감사 중 무엇인지 정한다. 주제 감사 범위를 현재 diff에만 가두지 않고, 작은 변경을 전체 레포 재작성으로 확대하지 않는다.
- 편집 중인 브랜치와 미커밋 변경을 확인한다. 검토를 위해 브랜치를 바꾸거나 다른 작업을 되돌리지 않는다. 이력이 있으면 필요한 기준의 파일을 읽기 전용으로 비교한다.
- 구현 사실은 코드·테스트·실행 결과, 제품 요구는 사용자 결정·승인된 명세, 외부 제약은 해당 버전의 공식 원문으로 확인한다. 같은 종류의 자료도 확인 날짜·버전·적용 범위를 맞춘다.
- 요구와 코드가 다르면 `문서의 오기 / 구현 결함 / 미확정 결정`을 구분한다. 문서 정리를 근거로 요구를 코드에 맞춰 낮추거나 구현되지 않은 정책을 현재 동작으로 쓰지 않는다.

## 양방향으로 대조한다

**문서에서 근거로:** 관련 페이지의 명령·옵션·기본값·예제·권한·실패 설명을 읽고 실제 정의와 호출 경로를 찾는다.
**근거에서 문서로:** 범위 안의 공개 API·설정·사용자 흐름·선택/폐기 기능을 찾아 독자가 어디에서 배울 수 있는지 확인한다.
같은 동작이 README·가이드·참조·예제에 반복될 수 있으므로 사용 위치까지 검색한다.

| 대조 항목 | 확인할 차이 |
|---|---|
| API·CLI | 이름·인자·자료형·필수 여부·기본값·반환·오류·호환성 |
| 설정·환경 변수 | 실제 소비 위치·우선순위·opt-in·보안 영향·지원 범위 |
| 사용자 흐름 | 정상·빈 값·권한 거부·중복·실패·복구의 관측 가능한 결과 |
| 실행 예제 | 실행 위치·선행 작업·필요 버전·입출력·부작용 |
| 현황·완료 주장 | 구현 여부·검사 대상·날짜·건너뜀·미확인 사항 |
| 결정·설계 | 확정/제안 상태·대체 이유·관련 구현/작업과의 연결 |

모든 항목을 모든 페이지에 요구하지 않는다. 변경된 계약과 그 소비자에 맞춰 고른다.
발견은 `페이지/절 → 문제 → 코드·결정·원문 위치 → 권장 변경 → 남은 확인`으로 남긴다.

## 필요한 곳만 갱신한다

- 동작·조건·예외가 이미 정확하면 문장을 보존한다. 새 내용을 적절한 기존 절에 넣고 중복 문서 생성을 피한다.
- 자동 생성 참조는 docstring·schema·원본 spec·generator 설정부터 확인한다. 허용된 원본을 고치고 등록된 생성 절차를 사용한다. 생성물만 편집해 다음 생성 때 사라지는 수정을 만들지 않는다.
- 번역이 수동인지 자동인지 확인한다. 기존 언어·번역 정책을 따르고 자동 번역 산출물을 임의로 수정하지 않는다. 번역 작업이 범위 밖이면 원본 변경과 후속 필요를 남긴다.
- 코드에 있지만 미출시인 기능은 현재 지원 기능으로 섞지 않는다. 레포의 릴리스 정책에 따라 예정 버전·개발 중 상태·지원 조건을 표시한다. 정책이 없으면 날짜만으로 출시됐다고 판단하지 않는다.
- 예전 문서는 당시 상태를 보존하고 현재 정본으로 연결한다. 새 문서를 만들었다는 이유로 과거 실험의 수치나 실패 기록을 현재 결과로 덮어쓰지 않는다.

## 예시

문서에는 CLI의 기본 재시도가 3회지만 현재 구현은 1회이고, 제품 결정은 최대 1회를 명시한다고 하자.
문서와 관련 예제를 고친 뒤 실제 파서·해당 동작의 근거를 확인한다. 도움말 확인만 했다면 재시도 동작을 실행 검증했다고 쓰지 않는다.
반대로 승인된 요구가 3회라면 문서만 1회로 고쳐 일치시킨 것을 해결 완료로 보고하지 않는다.

설계/구현의 차이를 다룰 때는 [명세 유지](specifications.md)에서 변경 권위·의도 변경/구현 결함/동작 보존 정리를 구분한다. 관련 설계의 R/O와 검토/검사·인덱스 연결을 확인하고 구현에 맞춰 요구나 Safeguards를 낮추지 않는다.
