# 문서 변경의 검증과 보고

검사는 변경한 문서의 역할·실행 영향·구조에 맞춰 고른다. 전체 보안 감사나 앱 E2E를 문구 수정마다 강제하지 않는다.
검증의 목적은 읽을 수 있는 문서와 정확한 근거 연결이며, 형식 통과를 사실성 보증으로 쓰지 않는다.

## 변경별로 확인한다

| 변경 | 필요한 확인 |
|---|---|
| 문구·용어·오탈자 | 의미·조건·계약 강도가 유지되는지, 주변 문맥·Markdown diff |
| 동작·명령·API·설정 | 실제 코드·도움말·schema·등록된 검사의 근거와 관련 예제 대조 |
| 이동·병합·제목 변경 | 고유 내용 보존, 이전→이후 대응, 인바운드 링크·앵커·목차·설정·이미지 |
| 생성 문서·navigation·사이트 문법 | 올바른 원본 편집 여부, 기존 생성/빌드·렌더러로 영향을 받는 부분 확인 |
| 위키 반영·종합 | 출처가 실제 주장을 지지하는지, 조건·버전·충돌·추정·원본 보존 |
| 인덱스·단계별 문서 지도 | 관련 원문에 도달하는지, 무관 본문을 따라 읽지 않는지, 누락/오래됨의 검색 fallback과 실제 task/근거 연결 |
| 스킬·읽기 선택 조건 | 메타데이터·참조·발견/선택, 관련 작업의 실제 사용과 무관한 작업의 불필요 로드 여부 |

## 링크·앵커·렌더링

- 대상 파일과 heading/anchor, 상대 경로, 대소문자, 이미지·include, navigation에서 들어오는 경로를 확인한다.
- 내부 Markdown의 앵커 생성 방식은 렌더러별로 다를 수 있다. 렌더러를 모르면 단순 slug 추측을 실제 렌더 결과로 보고하지 않는다.
- 문서 사이트가 있으면 기존의 관련 build/lint/link 명령을 사용한다. MDX·include·자동 참조는 단순 텍스트 검사와 실제 빌드의 결과를 구분한다.
- 외부 링크 확인 실패는 네트워크/인증/삭제 가능성을 구분하고 확인 불가로 남긴다. 무조건 링크를 삭제하거나 무관한 홈 페이지로 바꾸지 않는다.
- 브라우저 UI·레이아웃을 바꾼 경우에만 관련 렌더·사용자 흐름 확인을 추가한다. 텍스트 스킬 추가에 제품 앱 E2E를 요구하지 않는다.

## 명령·예제는 안전하게 확인한다

먼저 실행 위치·환경·필요 권한·부작용을 읽는다. 읽기 전용 도움말/정적 대조와 실제 실행 검증을 구분한다.
설치·삭제·migration·외부 전송·과금·운영 데이터 변경 명령을 문서 확인 목적으로 무작정 실행하지 않는다.
실행이 필요한 예제는 허용된 로컬 격리 환경과 합성 입력으로 확인한다. SSH로 접근하는 서버는 읽기 전용이며 원격 테스트·빌드·캐시 생성도 하지 않는다.
실행하지 못한 명령은 검증 방법·한계를 표시하고 성공했다고 쓰지 않는다. 새 검사 도구·사이트·CI를 문서 편집 때문에 자동 설치하지 않는다.

## 현재 레포에서의 연결 확인

루트에서 기존 도구를 사용한다. 작동하는 Python 가상환경이 있다면 그 interpreter를 사용한다.

```sh
python3 tools/harness/run.py skill validate docs-maintenance
python3 tools/harness/run.py doctor
python3 tools/harness/run.py context --kind implement --topic docs-organization --read
python3 tools/harness/run.py context --kind research --topic docs-index --read
python3 tools/harness/run.py context --kind review --topic docs-sync --read
python3 tools/harness/run.py context --kind research --topic wiki-query --read
python3 tools/harness/run.py check --paths .agents/skills/docs-maintenance/SKILL.md .agents/context.toml --plan
```

`doctor`가 내부 링크의 파일 존재를 확인해도 heading anchor·외부 URL·출처의 사실성까지 검증하는 것은 아니다.
현재 `context`의 kind/topic/path 조건은 OR이므로, 세부 절차를 모든 문서나 모든 연구에서 읽도록 넓게 등록하지 않는다.
`docs` 기본 조회는 진입점을, `docs-organization`·`docs-sync`·`wiki-query`는 해당 참조를 선택하는지 실제 결과를 읽는다.
인덱스 링크의 본문은 자동 포함되지 않는지, 같은 프로젝트 인덱스가 중복 출력되지 않는지, 인덱스가 없어도 기존 필수 본문 선택은 유지되는지 확인한다.
같은 질문의 실제 읽은 경로·문자/바이트량과 답변 근거를 비교한다. 이를 측정하지 않은 토큰 절감률로 바꾸지 않는다.
선택 설정이 바뀌면 관련 회귀 검사를 실행하고 무관한 작업에서 위키 갱신 절차가 선택되지 않는지도 확인한다.

## 최종 검토와 완료 보고

- 독자가 진입점에서 올바른 페이지를 찾아 전제→절차/결론→근거로 이동할 수 있는지 확인한다.
- 이동·요약 전후를 대조해 고유한 제약·실패 원인·사용자 정정·검증 결과가 보존됐는지 확인한다.
- 변경한 내용, 근거 위치, 실제 실행한 검사·대상·결과, 미실행·미해결·추가 결정만 보고한다. 검사 개수나 문서량으로 품질을 주장하지 않는다.
- 파일을 저장·등록한 상태와 실제 자동 실행·지속 갱신을 구분한다. 현재 요청에 없는 커밋·배포·메시지 전송을 완료 단계에 넣지 않는다.

설계/구현의 차이를 다룰 때는 [명세 유지](specifications.md)에서 변경 권위·의도 변경/구현 결함/동작 보존 정리를 구분한다. 관련 설계의 R/O와 검토/검사·인덱스 연결을 확인하고 구현에 맞춰 요구나 Safeguards를 낮추지 않는다.
