# 설계 정본·변경 방향·검토 근거 관리

요구/설계 문서를 만들거나 코드·결정과 맞출 때 읽는다. 의도/도메인/설계의 내용 판단은 [REASONS 절차](../../plan-project/references/reasons-canvas.md)가, 이 참조는 문서의 권위·최신화·연결을 맡는다.

| 확인한 차이 | 먼저 확인할 정본 | 수행할 것 |
|---|---|---|
| 요구·권한·관측 동작·고정 경계가 달라짐 | 실제 사용자 요청/결정·현재 요구/설계 | 영향받는 설계와 R/O를 먼저 갱신하고 관련 정렬을 재확인한 뒤 코드·검사를 수정 |
| 명세는 충분하고 구현만 위반 | 현재 명세·실제 실패 | 요구/Safeguards 의미를 유지하며 재현→좁은 코드 수정→회귀 |
| 이름/내부 구조 정리이고 동작 유지 | 기존 의도·계약·관련 회귀 | E/Structure/O의 구현 설명을 증분 동기화 |
| 설명·예제·링크 오기 | 실제 결정·코드/검사 | 필요한 문서·목차만 수정 |
| 어느 쪽이 맞는지 미결 | 결정 권위·버전·수용 조건 | 자동으로 일치시키지 말고 선택과 영향을 분리 |

## 의도 변경

intent-update는 변경 근거·영향 R/O·새/잔여 미결정을 보존한다. 구현을 정당화하려고 요구를 낮추거나 성공 조건을 지우지 않는다. 실제 결정이 충분하면 이미 맡긴 범위의 세부 승인을 반복하지 않는다.
설계를 고치면 이전 alignment의 SHA가 맞지 않는다. 활성 구현 흐름은 새 정렬 근거에서 재시작하며 옛 입력을 몰래 바꿔 통과시키지 않는다. 기존 설계/검토 원본이 완료 증거이면 당시 사본을 보존한다.

## 구현 설명 동기화

implementation-sync는 동작 보존 근거를 먼저 확인한다. 관련 구조·이름·구현 설명만 고치고 Requirements/Safeguards의 의미는 유지한다. 동작·권한·품질 경계가 달라졌다면 intent-update로 다시 분류한다.
작은 리팩터링을 이유로 전체 설계를 새로 생성하지 않는다. 무관한 규칙/위키 페이지나 기존 결정은 보존한다.

## 정본과 선택 읽기

- 요구/설계는 프로젝트의 brief·기존 설계/ADR 또는 필요한 기능별 Markdown이 정본이다. index는 그 위치·질문/단계·읽을 조건만 안내한다.
- 현재 R/O·관련 결정·검토를 task/evidence로 연결한다. task 상태나 채택된 지식의 별도 장부를 만들지 않는다.
- 현재 O의 구현/검증에는 공통 계약·선택한 O·필요한 경계와 원문만 읽는다. 모든 Canvas/위키를 context.documents에 강제로 넣지 않는다.
- 새/변경된 정본·관련 검토·확인 결과의 읽을 조건과 index를 갱신한다. 링크된 전체 본문은 자동 확장하지 않는다.
- 위키에는 설계 선택·대안/기각·재검토 조건과 실제 결과의 출처를 남긴다. 계획을 구현 사실로, 초안을 채택된 규칙으로 승격하지 않는다.

편집 후 [문서 검증](validation.md)에서 R→O→수용조건·검사와 현재 원문·버전·변경 방향을 대조한다. [구현 진입 검사](../../../../tools/harness/docs/reasons.md)는 파일/연결의 검증이며 의미적 합의·실제 사용자 신원·OS 파일 쓰기 권한 통제의 보장은 아니다.
