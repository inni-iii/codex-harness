# 인덱스에서 필요한 원문만 읽기

문서 찾기·인덱스 작성/정리·문서가 많아 탐색 비용이 큰 요청에서 읽는다.
목표는 판단에 필요한 근거를 빠뜨리지 않으면서 무관한 본문·중복 읽기를 줄이는 것이다.

## 읽는 순서

1. 현재 질문의 프로젝트·주제·단계·결정할 것을 정한다. 이미 정본 경로/절이 지정됐으면 그 부분으로 바로 간다.
2. 이 레포에서는 `docs/index.md`를 시작 지도로 사용한다. 프로젝트 작업은 선택한 workflow 옆 `index.md`, 하네스 사용법은 `tools/harness/docs/index.md`로 분기한다. 기존 프로젝트에 다른 이름의 진입점이 있으면 이를 재사용한다.
3. 지도에서 목적·읽을 조건·현재/초안/과거 상태를 보고 관련 정본을 고른다. 인덱스에 링크됐다는 이유로 모든 하위 문서를 읽지 않는다.
4. 선택한 본문의 관련 절·조건·예외를 읽는다. 주장을 확인하는 데 필요한 원본·호출자·반대 근거만 추가한다. 검색 snippet/한 줄 요약은 실제 원문 확인을 대체하지 않는다.
5. 이미 읽은 변경 없는 문서는 같은 대화에서 재사용한다. 코드·버전·결정이 바뀌었거나 다른 경계가 드러나면 해당 원문을 추가 확인한다.

프로젝트 요구·명시된 필수 문서·보안 맥락과 과거 세션 원문 확인 지시는 계속 따른다.
문서 개수·토큰/글자 수 상한을 맞추려고 관련 근거·실패 조건·반대 증거를 잘라내지 않는다.

## 작고 계층적인 지도

- 최상위에는 문서 영역·프로젝트 지도·현재 작업의 출발점만 둔다. 개별 파일이 많아지면 해당 영역의 하위 지도에서 관리한다.
- 하위 항목은 `질문/단계 → 정본 링크 → 읽을 조건 → 현재/초안/과거`를 짧게 적는다. 기본값·API 명세·검증 결과 전문은 원본에만 둔다.
- 작업 상태는 task.json/evidence, 실행 명령은 workflow/현재 사용법, 제품 결정은 해당 프로젝트 문서가 정본이다. 인덱스에 상태 장부를 복제하지 않는다.
- 새 페이지·이동·삭제·제목/적용 범위/정본 변경과 함께 해당 행·진입 링크를 갱신한다. 내용이 없는 예정 문서의 링크를 미리 만들지 않는다.
- 페이지·프로젝트가 늘어 상위 지도 자체가 읽기 부담이 되면 주제별 하위 지도로 분리한다. 고정 페이지 수나 파일 길이를 보편 기준으로 만들지 않는다.

## 누락·오래됨·선택 실패

인덱스가 없거나 링크/상태가 맞지 않으면 그 한계를 알리고 관련 폴더에서 `rg --files`, 제목·용어·심볼 검색으로 후보를 좁힌다.
`context`가 설정의 누락 파일·알 수 없는 주제로 실패하면 실패를 숨기지 않고 AGENTS/관련 스킬과 실제 원문을 직접 읽는다.
선택 실패를 이유로 전체 docs 전문을 한 번에 로드하지 않는다. 쓰기가 허용된 요청이면 확인한 지도·링크·규칙도 고친다.
읽기 전용 질문이면 원문으로 답하고 지도 보완 필요만 알린다.

## 도구와 효율의 실제 경계

이 레포의 `context`는 존재하는 `docs/index.md`와 선택한 workflow 옆 `index.md`를 본문 앞에 한 번 포함한다.
링크를 재귀로 펼치거나 의미를 판정해 자동 검색하는 기능은 아니다. 인덱스에서 고른 원문은 직접 열거나, 그 원문에 연결된 종류/주제/경로 규칙으로 다시 선택한다.
`--paths`는 규칙을 맞추는 입력이다. 임의의 문서 경로를 넘겼다고 그 문서 본문이 직접 읽히는 것은 아니다.
`context.documents`는 매 호출 필수 읽기다. 작은 지도·필수 개요 위주로 유지하고 긴 설계·운영·전체 위키를 단순 편의 때문에 모두 넣지 않는다.
상세 자료는 실제 읽을 조건으로 연결한다. 종류·주제·경로 조건은 OR이므로 `kinds=["implement"]`는 모든 구현에서 해당 문서를 읽게 할 수 있다.
기존 필수 목록과 자동 보안 문서를 인덱스 도입만으로 축소하지 않는다. 구조 변경이 필요하면 기존 요구를 먼저 확인한다.

효율을 확인할 때는 같은 질문에서 실제 읽은 경로·본문 문자/바이트량·필요한 답을 찾았는지를 비교한다.
문자량 감소를 모델 토큰/과금/전체 정확도의 절감률로 바꾸어 표현하지 않는다. 필수 지침·과거 원문 읽기의 비용도 숨기지 않는다.

설계/구현의 차이를 다룰 때는 [명세 유지](specifications.md)에서 변경 권위·의도 변경/구현 결함/동작 보존 정리를 구분한다. 관련 설계의 R/O와 검토/검사·인덱스 연결을 확인하고 구현에 맞춰 요구나 Safeguards를 낮추지 않는다.
