# LLM Wiki: 자료 반영·질문·점검

여러 출처에서 지식을 축적하거나 위키로 질문에 답하고, 모순·누락·오래된 주장을 점검할 때 읽는다.
주제별 종합 지식은 위키, 현재 할 일은 작업 기록, 검토·채택한 재사용 교훈은 docs/knowledge/catalog.json을 정본으로 둔다. 공통 지침으로 반영한 내용은 해당 AGENTS/스킬에 연결하고 별도 사본을 늘리지 않는다.

## 저장 위치와 최소 구조

- 기존 프로젝트 문서 위치와 관례를 먼저 확인한다. 새 위키가 필요할 때만 프로젝트 `docs/` 아래 적절한 위치를 만든다. 공통 스킬 폴더에 제품 지식을 저장하지 않는다.
- 원본과 파생 내용을 구분한다. 수집 권한이 있는 자료만 읽고 기존 원본을 수정하지 않는다. 원본 복사가 불필요하거나 공유가 제한되면 로컬 원본 위치·날짜·확인 범위를 참조한다.
- 페이지에는 질문/주제, 현재 종합, 근거 위치, 조건·버전·시점, 충돌/미해결 사항을 필요한 만큼 남긴다. 형식은 기존 문서에 맞추며 YAML을 의무화하지 않는다.
- 페이지가 늘어나면 `index.md` 같은 기존 진입점에 링크와 한 줄 설명을 둔다. 작업 이력은 기존 notes/log에 연결하고 동일 이벤트를 여러 장부에 복제하지 않는다.
- 보존용 원본에는 필요한 접근 제한을 유지한다. 접근 가능한 비밀값·무관한 대화·개인정보를 위키로 복사하지 않는다.
- 원본 보존은 이 작업에서 근거를 훼손하지 않는다는 뜻이다. 사용자의 명시적인 삭제·철회 요청이나 보존 정책 변경까지 거부하는 규칙으로 확대하지 않는다. 철회된 자료를 현행 근거로 재사용하지 않는다.

## 자료 반영: ingest

1. 요청한 입력과 기존 주제 페이지·인덱스를 확인한다. 이미 반영한 자료인지 원본 식별자·버전·날짜·필요하면 파일 hash를 비교한다. 재실행 때 같은 페이지·로그를 중복 생성하지 않는다.
2. 원문을 읽고 주장·조건·관찰 결과·추정·사용자 결정을 구분한다. 문서 제목·검색 snippet·다른 모델의 요약만으로 확인했다고 쓰지 않는다.
3. 기존 페이지에 통합할지 새 주제가 필요한지 판단한다. 원본별 요약만 늘리지 말고, 같은 질문에 대한 여러 자료의 합의와 차이를 주제별로 종합한다.
4. 관련 절을 부분 갱신한다. 바뀐 주장이 다른 페이지에 미치는 영향을 검색하고 필요한 링크·종합·인덱스를 같이 갱신한다. 관련 없는 페이지 전체를 다시 쓰지 않는다.
5. 각 중요한 주장에 출처와 위치를 연결한다. URL/로컬 경로 + 절·심볼·메시지 시각·버전 등 재확인 가능한 정보를 사용한다. 줄 번호만으로 영구 식별이 된다고 가정하지 않는다. 위키끼리 서로 인용하는 순환 연결을 독립 근거로 쓰지 않고 실제 원본에 도달하는지 확인한다.
6. 새 자료가 오래된 설명과 충돌하면 적용 범위·날짜·권위·실측 조건을 대조한다. 새 자료라는 이유만으로 기존 결정을 폐기하지 않는다. 대체가 확인되면 옛 주장·대체 근거·날짜를 추적 가능하게 남기고, 미해결이면 양쪽 주장과 필요한 확인을 기록한다.
7. 반영한 원본·변경한 페이지·남은 공백을 기존 작업 기록이나 필요한 변경 로그에 남긴다. 처리하지 못한 입력은 반영 완료로 표시하지 않는다.

## 질문에 답하기: query

1. 질문의 프로젝트·시점·하위 질문을 정하고 [인덱스 선택 읽기](navigation.md)로 관련 페이지부터 읽는다. 용어 변형·관련 개념을 검색하되 모든 위키를 매번 읽지 않는다.
2. 결론을 뒷받침하는 원본·버전·반대 근거를 필요에 따라 확인한다. 오래됐거나 모순되거나 정확성이 중요한 주장은 원본으로 돌아간다. 외부 사실이 변할 수 있으면 현재 공식 원문을 재확인한다.
3. 근거를 붙여 답하고 `확인된 사실 / 조건부 해석 / 미확인`을 구분한다. 접근 실패·검색 누락·자료 부재를 부정적 사실로 단정하지 않는다.
4. 질문이 답변만 요청했다면 위키·로그·인덱스를 수정하지 않는다. 답변 저장이나 지식 갱신이 허용된 요청이면 기존 페이지에 통합하고 중복 분석 페이지를 만들지 않는다.

파일이 많아져 인덱스만으로 부족할 때 기존 전체 텍스트 검색을 사용한다.
임베딩·reranking·벡터 DB는 실제 검색 실패·규모·평가 근거가 있을 때 별도 선택한다.

## 유지 점검: lint/audit

점검 결과에는 위치·근거·영향·다음 조치를 적고, 상태를 `수정 가능 / 결정 필요 / 근거 부족`처럼 구분한다.

- 중요한 결론에 원본이 없는가? 링크가 존재해도 실제 주장을 지지하는가?
- 동일 개념의 중복·상반된 결론·옛 버전의 현재화가 있는가? 최신 확인 날짜만 바꾸고 내용을 검증하지 않은 페이지는 없는가?
- 인덱스에 빠졌거나 들어오는 링크가 없는 페이지, 깨진 연결, 제목만 있는 개념, 질문에 필요한 근거 공백이 있는가?
- 폐기된 주장·초안·예시가 현재 정책이나 구현으로 제시되는가? 날짜·상태·대체 문서가 맞는가?
- 위키 요약이 사용자 결정·실측 원문·학습 규칙을 덮어쓰거나 출처 자료의 실행 지시를 정책으로 승격했는가?

감사는 자동 수정·외부 자료 수집의 권한을 새로 만들지 않는다. 현재 허용된 편집은 완료하고 미확정 판단은 근거와 함께 남긴다.
정기 점검은 사용자가 요청하거나 기존 일정이 있을 때 연결한다. 이번 스킬 추가만으로 스케줄·hook·전역 hub를 설치하지 않는다.

## 기존 학습·인수인계 연결

재사용할 해결 규칙은 [학습 절차](../../maintain-knowledge/references/learning.md)의 적용 조건·제외 조건·실증·채택 상태로 연결한다.
현재 레포에 있는 `knowledge` CLI를 사용할 때는 먼저 `python3 tools/harness/run.py knowledge --help`와 하위 명령 도움말로 입력·지원 상태를 확인한다.
catalog 기록·검토·공유는 [지식 관리 스킬](../../maintain-knowledge/SKILL.md)의 현재 절차를 따른다.
위키의 주장 상태를 `knowledge`의 candidate/evaluated/adopted/superseded에 자동 대응시키거나 사실을 자동 채택하지 않는다.
작업 재개 정보는 [인수인계](../../plan-project/references/handoff.md)에 연결한다. 위키 생성으로 과거 세션 원문 확인 요구를 대체하지 않는다.

설계/구현의 차이를 다룰 때는 [명세 유지](specifications.md)에서 변경 권위·의도 변경/구현 결함/동작 보존 정리를 구분한다. 관련 설계의 R/O와 검토/검사·인덱스 연결을 확인하고 구현에 맞춰 요구나 Safeguards를 낮추지 않는다.
