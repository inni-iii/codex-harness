# 짧은 요청에 적용하는 기본 검증 계약

“검증해줘”, “확인해줘”, “테스트해줘”와 범위를 생략한 동등한 요청을 받으면 적용한다. 짧은 요청을 단순 lint/check 한 번으로 축소하지 않는다. 현재 에이전트가 필요한 절차를 수행하며 별도 모델·자동 검사 worker·새 훅을 실행하지 않는다.

## 대상과 제한부터 복원

명시한 대상 → 현재 대화의 작업/산출물 → 연결한 task와 선택한 프로젝트/변경 범위 순으로 대상을 정한다. 이미 명확하면 범위를 다시 묻지 않고 짧게 알린 뒤 진행한다. 서로 다른 대상 중 선택에 따라 결과가 달라질 때만 구체적으로 질문한다.
“문서만”, “실행하지 마”, “수정하지 마” 같은 현재 제한을 우선한다. 검증은 새 설계·기능·인증 방식 변경·원격 쓰기·유료 호출·임의 설치 권한을 만들지 않는다.

## 필요한 검증을 선택하고 끝까지 수행

| 확인할 것 | 적용하는 행동과 근거 |
|---|---|
| 요구와 실제 실행 | 요구/기존 계약과 성공 조건을 읽는다. 코드·앱·CLI는 허용된 로컬 환경에서 실제 실행해 핵심 입력→처리→결과를 확인한다. 필요하면 저장/재조회도 확인한다. 문서/조사는 원문·조건·링크·예제와 결론을 대조한다. |
| 정상·실패 경로 | 실제 기능에서 관련된 잘못된 입력·빈 값·경계·권한·중복·외부 실패 등을 고른다. 기대 결과와 금지 부작용을 실제 처리 경계에서 확인한다. 모든 항목을 모든 작업에 강제하지 않는다. |
| 기존 기능과 회귀 | 영향받는 기존 소비자/테스트를 확인한다. 실제 결함은 [검토·보완 반복](follow-through.md)에 따라 재현→허용된 수정→같은 회귀와 주변 검사로 이어간다. 수정 금지면 재현/근거·후속을 남긴다. |
| 구조 | 요구 규모에 맞는 책임 분리·의존 방향·입출력/API 계약·오류/자원 정리를 관련 언어 스킬로 검토한다. 검증을 이유로 큰 재설계를 하지 않는다. |
| 보안 | [보안 스킬](../../security-review/SKILL.md)로 관련 입력·자원 권한·비밀·외부 응답·의존성/실행 경계를 확인한다. 앱 보안은 필요한 실제 허용/거부 사례로 검증하고 비밀 패턴/설정 검사만으로 대체하지 않는다. |
| 사용자 흐름 | 폼·탐색·인증·권한·프론트/API·공통 UI 행동이면 [E2E 스킬](../../e2e-testing/SKILL.md)로 의미 있는 사용자 결과를 얻는 관련 흐름을 실행한다. 문서·순수 계산 등은 비적용 이유를 짧게 남긴다. |

프로젝트 workflow/기존 실행·검사 명령부터 확인한다. 누락된 관련 테스트/연결은 현재 권한과 범위에서 보완한다. 하네스 자체 doctor/check만 통과한 것을 실제 앱 검증으로 바꾸지 않는다. 실제 앱 검사 미등록은 필요한 연결로 남긴다.
유효한 기존 결과는 대상 코드·환경·범위가 같으면 재사용하고 추가 변경/실패/불확실성 때만 관련 범위를 다시 검사한다. 전체 suite는 공유 영향·제출 범위·불확실성에 맞춰 선택한다. 작은 편집마다 전체 검사/E2E를 반복하지 않는다.

문서의 계약·사용법·현재 검증 요약이 달라졌으면 해당 프로젝트/기능의 기존 정본을 갱신하고 지도와 선택 조건도 같은 작업에서 연결한다. 새 배치 기능 문서는 [문서 저장 명령](../../../../tools/harness/docs/project-documents.md)을 사용한다. 매 검사마다 새 Markdown 보고서를 만들지 않고 원본 로그는 `.runtime/`, 작업 이력은 기존 task/notes에 둔다.

## 결과와 다음 행동

프로젝트 설명 문서가 있으면 [설명 누적 절차](../../plan-project/references/project-explanation.md)에 따라 현재 결과와 한계를 갱신한다. 검사 파일의 존재와 실제 실행을 구분하고, 코드가 바뀌어 근거가 오래된 설명/문답은 갱신 필요로 표시한다. 중간 검증에서는 새 문답을 만들지 않고 최종 정리 때만 현재 근거에서 도출한다.

실행·정상/실패·회귀·구조·보안·관련 E2E 각각의 적용 여부와 실제 근거를 대조한다. 명령·cwd·대상 상태·실행 수/실패/skip·핵심 관측·미실행/차단을 짧게 보고한다. 0개/전체 skip/실행 불가를 통과로 쓰지 않는다. 필수 미확인은 남은 상태와 다음 행동을 연결한다.
기록을 만드는 검증은 `verify-work:inspect`에서 request만으로 시작할 수 있다. 이는 읽기 검증 진입이며, 실제 수리에 들어가면 현재 의도/경계를 경량 설계로 확인하고 기존 `verify-work:repair`의 design/alignment를 연결한다. 기존 구현 후 `verify-work:check`의 준비/증거 계약도 유지한다. 검증만 요청한 결과물에 새 설계 문서를 먼저 쓰도록 강제하지 않는다.
