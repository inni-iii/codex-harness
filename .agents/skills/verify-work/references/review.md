# 요구 충족과 결함을 나누어 리뷰

코드 변경의 완료 검토나 명시적인 리뷰 요청에서 읽는다.
하나의 성공 사례에 고정되지 않도록 검토 질문을 두 묶음으로 나눈다.
같은 테스트를 두 번 실행하거나 두 에이전트를 반드시 쓰는 절차가 아니다.

## 1. 요구 충족 확인

사용자 요청·프로젝트 계약·작업 수용 기준을 먼저 읽는다.
각 기준에 대해 실제 바뀐 동작과 관측 근거를 연결한다.

| 기준 | 구현 위치/실제 동작 | 근거 | 판정 |
|---|---|---|---|
| 입력 오류 후 수정 가능 | 해당 입력과 오류 처리 경로 | 행동 검사/브라우저 결과 | 충족·불충족·미확인 |
| 기존 조회 유지 | 기존 소비자와 API 계약 | 관련 회귀 결과 | 충족·불충족·미확인 |

위 행은 예시다. 구현에 없는 요구를 빠뜨렸는지와 요청 밖 기능을 추가했는지도 본다.
함수 이름·주석·완료 선언을 관측 결과로 대신하지 않는다.
설명·설계 문서만 요청된 경우에는 해당 산출물의 요구와 근거를 대조한다.

## 2. 결함·회귀 확인

diff와 호출자를 읽고 데이터 흐름·공유 경계·오류·취소·기존 기능을 확인한다.
검토할 위험을 먼저 고른 뒤 관련 원문과 검사를 좁힌다.

- 정상 흐름을 우회하는 입력·빈 상태·최대/최소·null/누락
- 오류를 성공처럼 바꾸는 catch·fallback·기본값
- 공유 자원·동시성·중복·부분 완료·정리 누락
- 인증/소유권·비밀값·외부 URL·업로드 경계
- 기존 호출자·생성 타입·설정·진입점·호환성
- 테스트가 구현을 통째로 mock하거나 넓은 예외를 허용해 결함을 가리는지

## 언어·도구별로 필요한 확인

Python이면 Python/프레임워크 버전과 실제 lint/type/test 설정부터 읽는다.
구체적 예외·가변 기본값·import 부작용·비동기 경로의 동기 I/O·취소/정리·거래 단위를 확인한다.
Svelte이면 상태 소유권·SSR 격리·반응성·요청 경합·UI 상태·키보드 계약을 확인한다.
파일 이동이면 import·설치 진입점·작업 디렉터리·테스트 수집이 유지되는지 본다.

ruff·mypy/pyright·pytest·프론트 검사는 프로젝트에 실제 정의된 명령만 사용한다.
형식·문서 스타일·타입 누락만으로 장애와 같은 심각도를 부여하지 않는다.
커버리지 비율을 일괄 80/90%로 만들거나 모든 변경에 전체 검사를 실행하지 않는다.

## 근거 재사용과 발견 보고

현재 대상·명령·조건에 유효한 기존 테스트 결과는 재사용한다.
새 결함 가설이나 미확인 경계가 생겼을 때만 추가 검사/좁은 재현을 한다.
실패를 고쳤으면 바뀐 범위에 해당하는 검사를 다시 수행한다.

발견은 파일·위치 → 발생 조건 → 사용자/데이터 영향 → 재현/근거 → 수정 방향 순서로 쓴다.
심각도는 실제 영향·가능성·영향 범위·복구 가능성을 근거로 정한다.
확인된 결함, 의심 사항, 범위 밖 기존 문제, 선택적 개선을 구분한다.
발견 없음은 읽은 범위와 수행한 검사에 한정한다. 미확인 기준이 남으면 완료로 판정하지 않는다.

구현 전에는 [설계/정렬](../../plan-project/references/reasons-canvas.md)의 현재 R/O·경계·미결정과 수용 기준을 대조한다. 구현 후에는 실제 결과를 그 기준과 대조하며 구현을 정당화하려고 설계·요구를 낮추지 않는다.
