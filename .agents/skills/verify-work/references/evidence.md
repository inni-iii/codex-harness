# 검증 근거 판정

실행·결과 재사용·커밋 검증을 할 때 읽는다.

## 통과 조건

종료 코드 0, 의도한 대상·명령·환경, 실행된 검사, 실패 없는 원본 결과를 함께 확인한다.
lint·build는 종료 코드 검사이고 테스트는 실행 수·skip·실패를 추가로 확인한다.
0개 테스트·전체 skip·누락 보고서·collect 실패·시간 초과를 통과로 보고하지 않는다.
일부 skip이 있으면 이유와 요구 범위를 확인한다. 이번 수용 기준 검사가 skip된 경우 전체 suite가 green이어도 해당 기준은 미검증이다.
외부 도구의 retries·xfail·quarantine이 최종 초록색 뒤에 실패를 숨겼는지도 확인한다.

JUnit 보고서는 실행별 새 {report} 경로를 쓴다.
중첩 testsuites의 요약 숫자를 합산하면 중복될 수 있으므로 실제 testcase를 기준으로 센다.
하네스는 case의 failure/error와 suite error를 보고 종료 코드가 0이어도 실패시킨다.
테스트 수만으로 주장 전체가 검사됐다고 판단하지 않는다.

## 로그와 보고

[검증 도구](../../../../tools/harness/docs/verification.md)는 .runtime/checks에 다음을 보존한다.

- 대상 소스·환경의 fingerprint와 범위·워크플로
- 실행 argv·cwd·선택 이유·종료 코드·소요 시간
- 파악 가능한 테스트 수·실패·skip
- 원본 로그·JUnit 파일·최종 상태

로그를 head/tail로 잘라 원래 프로세스 종료 코드 대신 파이프의 코드를 보고하지 않는다.
긴 로그는 파일에 남기고 필요한 실패 구간만 읽는다. 원본에 비밀값이 나올 수 있는 명령부터 피한다.
비밀이 포함된 원본·브라우저 trace는 공유하거나 Git에 넣지 않는다.

## 결과 재사용

캐시는 명시적 --reuse와 cacheable=true일 때만 사용한다.
소스·테스트·설정·환경의 fingerprint가 바뀌면 재실행한다. 실행 중 코드가 바뀌면 stale이다.
외부 DB·서버·시간·네트워크·브라우저 설치 상태는 소스 fingerprint로 증명할 수 없다.
이런 검사는 cacheable=false를 유지하거나 실제 조건까지 별도 관리한다.
node_modules/.venv의 모든 파일을 해시하지는 않으므로 수동 설치 변경 뒤에는 캐시를 쓰지 않는다.

## 정확한 커밋 대상

커밋 검증 요청이면 의도된 index를 확인하고 check --staged로 내보낸 사본을 검사한다.
worktree의 통과가 index 사본의 통과를 의미하지 않는다.
빠진 untracked helper·unstaged 테스트·로컬 의존성이 실패를 숨길 수 있다.
하네스는 자동 git add를 하지 않는다. 사본에 필요한 앱 의존성을 잠금 파일로 설치하는 절차는 프로젝트에서 준비한다.
사본에 worktree의 .env/node_modules/.venv를 연결하지 않는다.

## 실패와 완료

요구/검사 결함, 구현 회귀, 기존 결함, 환경·도구 실패를 구분한다.
로그에서 원인을 찾고 요청 범위 안에서 보완한다. 확인 없이 재실행만 반복하지 않는다.
보고에는 완료 기준별 근거와 남은 한계를 적는다. 하네스의 product_accepted는 자동 true가 되지 않는다.
