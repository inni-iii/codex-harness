# 영향 범위에서 검사 고르기

변경 파일만 보는 편향을 줄이되 매 작업 전체 검사를 반복하지 않는다.

## 요구에서 먼저 항목 도출

완료 기준 → 관측할 결과 → 정상/실패/경계 → 영향받는 기존 기능을 적는다.
그 다음 구현과 diff를 보고 항목을 보완한다. 구현을 읽으며 떠올린 성공 사례만 검사하지 않는다.

| 변경 | 가까운 검사 | 범위를 넓힐 조건 |
|---|---|---|
| 순수 업무 함수 | 기존 단위·관련 회귀 | 공통 정책·여러 호출자의 의미 변경 |
| API schema·생성 타입 | 계약·프론트 타입 검사 | 양쪽 통합·주요 사용자 흐름 |
| 인증·공유 설정·의존성 | 관련 영역의 공통 검사 | 서버 시작·대표 권한·프론트 연결 |
| 공용 UI·토큰·layout | 컴포넌트·정적 검사 | 대표 화면·주변 화면·반응형 |
| DB schema·query | 제약·transaction·조회 | 로컬 migration·기존 데이터 호환 |
| 연구 문서·스킬 | 원문·참조·명령·판단 예시 | 도구 변경 검사·실제 작업 평가 |
| 문구·링크만 변경 | 링크·현재 동작과 일치 | 실행 설정까지 바뀐 경우 |

검사가 없다고 아무 명령이나 등록하지 않는다. 요구 동작을 확인하는 실제 검사를 만들거나 미검증으로 남긴다.
HTTP health 200만 확인하는 스모크가 저장·권한·사용자 흐름까지 증명하지는 않는다.

## 전체 프로젝트를 보면서 실행은 선택하기

입력→업무→저장/외부→API→프론트까지 이번 변경이 건너는 경계를 표시한다.
공유 변경은 프로젝트 프로필의 impacts로 명시한다.
핵심 연결을 짧게 확인하는 app smoke를 always=true로 등록하면 행동 변경 때 함께 실행할 수 있다.
비싼 전체 E2E·빌드는 tier=full로 두고 제출·공유 변경·불확실성이 필요한 때 선택한다.
해당 full 검사가 특정 공유 변경 때 꼭 필요하다면 impacts에서 명시적으로 선택한다.

선택 도구는 경로 규칙만 본다. 호출 관계를 자동 추론하지 않으므로 새로운 경계를 발견하면 규칙도 보완한다.
미등록 파일은 needs_configuration으로 차단한다. 문서 예외에 모든 docs/projects/**를 넣어 숨기지 않는다.
전체 등록 검사도 등록되지 않은 기능까지 보장하지 않는다.

## 반대 관점 확인

구현 완료 뒤 요구 원문을 다시 읽고 다음 중 관련 항목을 대조한다.

- 잘못된 입력·빈 결과·최대/최소·오래된 상태
- 비소유자·익명·다른 사용자
- 중복 요청·동시성·취소·부분 실패
- 이전 기능의 소비자·생성물·설정·진입점
- 오류를 잡고 빈 결과로 바꾼 곳, fallback 때문에 실패가 감춰진 곳

모든 작업에 이 항목을 전부 강제하지 않는다. 적용한 관점과 제외 이유를 필요한 만큼 남긴다.
