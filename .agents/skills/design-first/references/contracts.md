# 디자인 기준과 컴포넌트 계약

기준 설정·공용 UI 변경·화면 비교에서 읽는다.

## 기준의 권위

현재 사용자 지시를 우선하고, 프로젝트가 승인한 문서·토큰·컴포넌트·화면 중 무엇이 기준인지 명시한다.
탐색용 mockup·외부 레포·블로그 예시를 승인된 기준으로 승격하지 않는다.
기존 코드와 승인 기준이 다르면 현재 값·기준·차이·영향을 확인한다.
현재 요청이 그 수정을 포함하면 진행하고, 서로 충돌하는 승인 기준처럼 결과가 갈리는 부분만 질문한다.
“원본 스킬이 모든 변경에 승인을 요구한다”는 이유로 그 승인 절차를 범용적으로 가져오지 않는다.

## 최소 디자인 체계

작은 프로젝트에서도 아래 연결은 설명할 수 있게 한다.

```text
기초 값: 색·간격·서체·radius 등
  → 의미 토큰: surface/text/action/danger 등
  → 공용 컴포넌트: props·변형·상태·접근성
  → 기능 화면: 도메인 데이터와 사용자 흐름
```

모든 값에 별도 component token을 만들 필요는 없다. 반복되는 의미와 변경 범위에 맞춘다.
원시 색 값을 여러 화면에서 복제하는 대신 의미 토큰으로 연결한다.
다른 레포의 브랜드 값·Figma 키·로컬 자산 경로·도메인 문구는 가져오지 않는다.

## 컴포넌트 계약 예시

| 역할 | 정할 계약 | 확인할 동작 |
|---|---|---|
| 버튼 | variant/size/type/loading/disabled | 의도치 않은 submit·연속 클릭·busy 안내 |
| 입력 | value/변경 이벤트/error/readonly | label·입력 보존·오류 연결·focus |
| 선택 | options/value/disabled | 키보드·긴 label·팝업 clipping |
| dialog | open/닫힘 조건/title | focus 진입·복원·Escape·스크롤 |
| 상태 안내 | success/error/info 의미 | 낭독·중복 안내·색 외 표시 |

예시의 props 이름·픽셀 규격은 프로젝트에서 정한다. 기존 호출자와 호환성을 검토한다.
primitive는 라우트·API client·특정 도메인 store를 직접 알지 않게 조합한다.

## 살아 있는 자료

실제 토큰 파일과 컴포넌트 데모를 기준 문서에서 연결한다.
토큰 표가 있다면 코드에서 확인한 값과 미결정 값을 구분하고 중복 복사본을 늘리지 않는다.
Figma가 있을 때만 코드↔디자인 연결을 유지한다. 없는 프로젝트에 파일 생성을 강제하지 않는다.

## 변경을 검증하기

바뀐 토큰/variant → 대표 컴포넌트 → 사용 화면을 추적한다.
해당 상태·뷰포트·테마·긴 텍스트에서 비교하고 screenshot 위치와 비교 기준을 기록한다.
전역 폰트·root 변수·app shell 변경은 주변 화면 영향과 되돌릴 단위를 함께 본다.
이번 작업에서 실제로 본 범위를 넘어서 디자인 일치를 주장하지 않는다.
