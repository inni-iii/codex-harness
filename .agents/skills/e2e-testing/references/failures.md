# E2E 실패를 분석하고 재검증

첫 실패의 assertion·서버 로그·trace·screenshot·대상 코드 상태를 보존한다.
실패 시 artifact 위치와 실행 명령을 보고한다. trace가 없으면 있었다고 하지 않는다.

| 증상 | 확인할 원인 |
|---|---|
| 서버 시작 실패 | 실제 명령·cwd·포트·환경·readiness·설치된 의존성 |
| locator timeout | 잘못된 접근 이름·화면 상태·API 실패·인증·렌더링 오류 |
| 응답 대기 timeout | 대기 등록 순서·URL/메서드·실패 응답·클라이언트 요청 발생 여부 |
| 로컬만 통과 | 기존 서버/데이터·개인 세션·잠금 파일·브라우저/환경 차이 |
| 간헐 실패 | 응답 경합·공유 데이터·병렬 실행·정리·실제 제품 결함 |
| 예상 외 screenshot 차이 | 폰트·viewport·테마·시간/동적 데이터·실제 UI 변경 |

timeout 증가·sleep 추가·retry·skip을 첫 해결책으로 삼지 않는다.
관측된 조건에 맞춰 대기·데이터 격리·제품 결함을 수정한다.
불안정성 재현이 필요하면 목적과 횟수를 정해 반복하고 각 실패를 남긴다.
재시도 후 성공을 첫 시도 성공으로 바꾸지 않는다. 중요한 흐름의 flaky/skip은 미확인으로 다룬다.
템플릿은 retries=0으로 시작한다. 재시도가 필요하면 최초 실패 기록과 flaky 판정 정책도 정한다.

0개·전체 skip·누락 보고서·수집 오류는 통과가 아니다.
브라우저·네트워크·서버 데이터가 바뀌는 결과는 캐시 재사용을 기본으로 하지 않는다.
수정 후 관련 시나리오부터 실행하고 공통 계약 변경이면 대표 기존 흐름까지 넓힌다.
실제 앱이 없을 때 실행한 작은 도구 fixture를 프로젝트 E2E 통과로 보고하지 않는다.
