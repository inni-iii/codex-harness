# 사용자 흐름과 테스트 데이터

## 요구에서 시나리오 고르기

| 변경 | 먼저 확인할 흐름 | 관련 회귀 |
|---|---|---|
| 생성/수정 폼 | 입력→제출→실제 반영→필요한 재조회 | 필드 오류·중복 제출·실패 후 수정/재시도 |
| 라우팅·공통 UI | 직접 URL·이동·뒤로가기·새로고침 | 대표 인접 페이지·키보드·좁은 화면 |
| 인증·권한 | 유효/없음/만료된 세션 | 다른 사용자 자원·로그아웃 후 재접근 |
| API 계약 | 실제 서버 응답을 UI가 사용 | 오류 분기·빈 결과·생성 타입/기존 소비자 |
| 비동기 검색/스트림 | 최신 결과·부분 결과·종료 | 역순 응답·화면 이탈·취소·재연결 |

이 표의 기능을 프로젝트 요구로 추가하지 않는다. 해당하는 항목을 선택한다.
E2E는 적은 핵심 경계를 끝까지 연결하고 세밀한 조합은 단위/통합 검사로 보완한다.
실제 API와 저장 경계를 증명할 때 그 경계를 전부 mock하지 않는다.
mock 검사도 유용하지만 실제 연결 검사와 별도로 표시한다.

## 데이터·인증 격리

합성 데이터·테스트 계정을 쓰고, 테스트별 고유 자원과 정리 주체를 정한다.
테스트 순서·이전 실행의 데이터·개인 로그인 세션에 의존하지 않는다.
인증 storage state·쿠키·trace·screenshot은 민감할 수 있다. .runtime 등 Git 제외 경로에 둔다.
실서비스 데이터를 fixture로 복사하거나 결제/이메일 등 외부 부작용을 실제 운영 대상으로 호출하지 않는다.
프로젝트에 없는 계정·DB·reset endpoint를 임의로 가정하지 않는다.

## 작성

role/label 같은 사용자 의미 locator와 자동 대기 assertion을 우선한다.
API 응답/팝업/다운로드 대기는 동작 전에 등록한다.
고정 sleep이나 networkidle 하나로 준비 상태를 판단하지 않는다.
status뿐 아니라 실제 요구 payload·표시·저장 의미를 확인한다.
관련 pageerror·실패 요청도 확인하되 예상된 거절 응답과 결함을 구분한다.

구체적인 대기·응답 assertion은 [Playwright 작성 예시](writing.md)를 필요한 때 읽는다.

POM은 반복 동작이 생겼을 때 추출한다. 모든 테스트에 별도 클래스를 강제하지 않는다.
처음에는 필요한 Chromium 시나리오부터 확인하고 프로젝트 지원 요구에 따라 모바일/다른 브라우저로 넓힌다.

공식 근거: [테스트 작성 원칙](https://playwright.dev/docs/best-practices), [인증 격리](https://playwright.dev/docs/auth).
